# Стартовий документ розробки: Система управління ІТ-задачами та зверненнями

> Базується на: «Технічне завдання на розробку системи управління ІТ-задачами та зверненнями», версія 3.1 (аналог функціоналу Redmine, адаптований під потреби ІТ-підрозділу).
> Призначення цього документа — операціоналізувати ТЗ у формат, придатний для запуску розробки: беклог за модулями, модель даних, план спринтів, критерії готовності.

---

## 0. Коротке резюме проєкту

Веб-система управління ІТ-проєктами, задачами, інцидентами та зверненнями співробітників. Основний акцент — на експлуатаційних процесах ІТ-підрозділу (планування робіт, контроль виконання, облік часу, база знань, звітність, SLA, інтеграція з Microsoft Active Directory).

**Ключові параметри:**
- Основний функціонал — до **50** облікових записів (сисадміни, керівники ІТ, оператори підтримки).
- Портал тікетів — **необмежена** кількість заявників (усі співробітники організації).
- Стек: **PHP 8.x (Laravel/Symfony) + MySQL 8.x**, без контейнеризації, односерверне розгортання.
- Розробка ПЗ (версії/релізи продукту, VCS-інтеграція) — **поза межами системи**.

## 1. Технологічний стек і базові рішення

| Компонент | Рішення |
|---|---|
| Backend | PHP 8.x, фреймворк **Laravel** (рекомендовано для швидкого старту MVP) або Symfony |
| БД | MySQL 8.x |
| Frontend | HTML/CSS/JS, шаблонізація Blade (PHP), опційно Vue.js для інтерактивних компонентів (канбан, Гант) |
| Пошук | MySQL FULLTEXT-індекси |
| Черги/фонові задачі | Laravel Queue (database-драйвер на старті, за потреби — Redis) |
| Файлове сховище | Локальна файлова система сервера |
| Автентифікація | Локальна (Laravel Breeze/Fortify) + LDAP/AD-модуль (наприклад, `directorytree/ldaprecord-laravel`) |
| Веб-сервер | Nginx + PHP-FPM |
| Розгортання | Один сервер Linux, без Docker/Kubernetes |

**Рішення, які потрібно зафіксувати на старті (Sprint 0):**
- [ ] Обрати фреймворк остаточно (Laravel vs Symfony) і зафіксувати версію PHP.
- [ ] Визначити структуру репозиторію та гілкову стратегію для самої команди розробки (внутрішня, не входить у функціонал продукту).
- [ ] Підготувати сервери під dev/test/prod (навіть якщо це один сервер з різними інстансами/портами).
- [ ] Налаштувати базове CI (лінтер, автотести) — інструмент на розсуд команди.

## 2. Модель даних (ключові сутності)

На основі п. 2.14 ТЗ («Вимоги до даних і зберігання»). Це відправна точка для проєктування схеми MySQL — деталізується на етапі проєктування.

- **User** (обліковий запис): ім'я, email, роль(і), група(и), джерело автентифікації (local/AD), статус активності, дата створення/деактивації.
- **Role / Permission**: рольова модель RBAC, права на рівні проєкту.
- **Project**: назва, батьківський проєкт (ієрархія), видимість, статус (активний/архівний), шаблон.
- **Task/Issue**: тип (інцидент, запит на обслуговування, проблема, планове завдання), статус, пріоритет, автор, виконавець, дедлайн, оціночний/фактичний час, батьківська задача, зв'язки з іншими задачами, теги.
- **Comment**: прив'язка до задачі/тікета, автор, текст (Markdown), згадування користувачів.
- **Attachment**: файл, власник, прив'язка до задачі/тікета/wiki-сторінки/проєкту.
- **TimeLog**: задача, користувач, дата, тривалість, категорія активності.
- **WikiPage**: проєкт, ієрархія, версії, вміст (Markdown).
- **Ticket**: окрема сутність або підтип Task — заявник (може бути без облікового запису основного функціоналу), черга/категорія, SLA-мітки (час першої відповіді, час вирішення), статус, CSAT-оцінка.
- **SLA Policy**: черга/категорія, цільовий час реакції, цільовий час вирішення, правила ескалації.
- **AuditLog**: об'єкт, тип дії, автор, час, деталі змін (діф).
- **Notification**: користувач, подія, канал (email/вебхук), статус доставки.

**Для кожного об'єкта обов'язково:** дата створення, дата останньої зміни, автор, відповідальний, поточний статус, журнал змін (аудит) — вимога з п. 2.14 ТЗ.

**Відкрите питання для проєктування:** строки зберігання архівних задач/тікетів/вкладень/журналів аудиту — визначити з замовником до фіналізації схеми БД.

## 4. Ролі системи (для тестових акаунтів і прав доступу)

| Роль | Ключові права |
|---|---|
| Адміністратор системи | Повний доступ, керування користувачами й налаштуваннями |
| Керівник ІТ-підрозділу | Управління проєктами/задачами/звітністю, аналітика |
| Системний адміністратор (виконавець) | Робота з призначеними задачами/інцидентами, облік часу |
| Оператор служби підтримки | Обробка тікетів, черги, контроль SLA |
| Спостерігач | Перегляд без редагування |
| Заявник (співробітник) | Подання тікетів, перегляд статусу власних звернень |

## 6. Критерії приймання / Definition of Done

Для кожного епіка з розділу 3 задача вважається виконаною, якщо:
- [ ] Функціонал відповідає відповідному пункту розділу 2 ТЗ.
- [ ] Є автотести (мінімум — критичні сценарії: створення/зміна статусу задачі, тікета, авторизація).
- [ ] Пройдено функціональне тестування на профілі навантаження до 50 користувачів основного функціоналу.
- [ ] Немає відкритих критичних/блокуючих дефектів.
- [ ] Оновлено технічну документацію (адміністратора та/або користувача).

**Загальні критерії приймання Системи** (з ТЗ, розділ 7):
- Матриця відповідності вимог (кожна вимога → тестовий сценарій → результат → статус), що охоплює модулі проєктів, задач, тікетів, SLA, ролей/доступів, AD, обліку часу, звітності, сповіщень, резервного копіювання.
- Успішне розгортання на PHP + MySQL без контейнеризації в test/prod середовищах.
- Технічна документація українською мовою.
