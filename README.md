# ITSM System

Легкий PHP-застосунок (без Composer/фреймворку) для управління ІТ-проєктами, задачами та зверненнями, згідно з ТЗ v3.1. Розроблено для системних адміністраторів та керівників ІТ-підрозділу — не для команд розробки ПЗ (без інтеграції з системами контролю версій, без релізного циклу продукту).

Поточну версію застосунку видно у футері веб-інтерфейсу та у файлі `VERSION` у корені проєкту.

📘 Окремі покрокові інструкції (Markdown + Word-версії в `docs/`):
- [`docs/ADMIN_GUIDE.md`](docs/ADMIN_GUIDE.md) / `docs/ITSM_Admin_Guide.docx` — для адміністратора системи (керування користувачами, проєктами)
- [`docs/USER_GUIDE.md`](docs/USER_GUIDE.md) / `docs/ITSM_User_Guide.docx` — для звичайних користувачів (робота з проєктами, задачами, обліком часу)
- [`docs/GIT_GUIDE.md`](docs/GIT_GUIDE.md) / `docs/ITSM_Git_Guide.docx` — як ініціалізувати git та відправити проєкт на GitHub
- `docs/ITSM_System_Documentation.docx` — Word-версія цього ж README, для друку чи надсилання поштою

## Реалізовано

**Основа**
- Автентифікація (локальна та через Active Directory, сесійна), рольова модель (RBAC): `admin`, `unit_admin` («Адміністратор Підрозділу» — повний доступ до даних і користувачів власного підрозділу — AD OU або підрозділ локального користувача, розділ 24 посібника адміністратора: проєкти/задачі/тікети, канбан, Гант, облік часу, черги, CSAT, журнал аудиту й користувачі підрозділу — лише в межах підрозділу), `it_manager`, інші ролі
- Особистий кабінет користувача (`/profile`) — власні дані, самостійна зміна пароля з підтвердженням поточного (недоступно для облікових записів з автентифікацією через AD)
- Блокування облікового запису після кількох невдалих спроб входу — кількість спроб і тривалість блокування налаштовуються через `/admin/security`; блокування прив'язане до конкретного користувача, не до IP
- Журнал аудиту дій із проєктами, задачами й тікетами, з переглядом через веб-інтерфейс (`/admin/audit`) — фільтри за типом сутності/автором/датою, українські підписи, розшифровані назви замість технічних ID
- Інтеграція з Active Directory — вхід AD-користувачів під доменним паролем (перевіряється напряму в каталозі через bind; копія пароля в системі не зберігається; те саме блокування після невдалих спроб, що й для локальних акаунтів), фонова синхронізація користувачів (`bin/sync-ad-users.php`, cron): створення, оновлення, зіставлення за стабільним `objectGUID` поряд з email (зміна пошти в AD оновлює акаунт, а не створює дубль), прив'язка до організаційного підрозділу (OU) з DN користувача, роль за відповідністю груп AD ролям (її можна закріпити вручну — синхронізація не змінить), деактивація зниклих з каталогу (вручну деактивованого користувача синхронізація не вмикає знову). Локальні акаунти синхронізація не чіпає ніколи. Підключення налаштовується формою в `/admin/ad` (сервер, домен, службовий акаунт, пароль, шифрування, перевірка сертифіката) — форма сама записує значення в `.env`. Потребує розширення `ext-ldap` (власного LDAP-протоколу, на відміну від IMAP/SMTP, не реалізовано свідомо). Безпарольний вхід (SSO, Kerberos) увімкнено окремо: автентифікацію виконує Apache (`mod_auth_gssapi`) на адресі `/sso/login`, застосунок лише зіставляє передане ім'я з AD-користувачем (`AD_SSO_ENABLED`, `AD_SSO_REALM`; налаштування — `docs/ADMIN_GUIDE.md`, розділ 23); за замовчуванням вимкнено — вхід формою
- Content-Security-Policy — суворий `script-src` (одноразовий nonce на запит, без `unsafe-inline`; дозволені лише власні скрипти та два CDN — jsdelivr і cdnjs), заборона вбудовування в чужі iframe, `X-Content-Type-Options`, `Referrer-Policy`. Усі вбудовані обробники подій (`onclick=` тощо) замінено двома делегованими: `data-confirm` на формах (діалог підтвердження) і клас `.auto-submit-select` на списках (миттєве надсилання форми)
- **Адмін-панель з двох розділів** — «Керування» (`/admin/manage`: проєкти, задачі всіх проєктів, черги тікетів, CSAT) і «Налаштування системи» (`/admin/settings`: користувачі, безпека входу, Active Directory, пошта → тікети, журнал аудиту), кожен зі своєю адресою й вкладкою; доступ, як і раніше, лише в адміністратора. Приналежність сторінок до розділів — в одному місці, `App\Core\AdminNav`
- **Журнал і сторінка помилок** — необроблена помилка не дає порожньої «HTTP 500»: користувач бачить код інциденту, **адміністратор — ще й причину** (клас, повідомлення, `файл:рядок`), а запис зі стеком потрапляє в `storage/logs/app-РРРР-ММ-ДД.log` (30 днів; без паролів, рядка запиту й аргументів функцій). Обробник не залежить від БД і шаблонів, тож працює навіть коли вони зламані
- **Обмеження частоти запитів (rate limiting)** для публічного порталу `/support` (звернення, коментарі, оцінки, перебір посилань відстеження — за IP, з урахуванням довірених проксі `TRUSTED_PROXIES`) і для публікацій на форумі (за користувачем); відповідь 429 із `Retry-After`; збій лічильника ніколи не блокує користувачів. Вимкнення — `PORTAL_RATE_LIMIT=false`
- Захист від CSRF на всіх формах, валідація значень з обмеженим переліком, захист від session fixation
- Пошук у списках вибору людини — виконавець задачі, відповідальний за проєкт, оператор тікета й оператор за замовчуванням для черги: клік по полю показує весь список, а набір тексту звужує його (без урахування регістру, кілька слів у будь-якому порядку, збіги підсвічені; Enter/клік обирає, Esc скасовує). Без JavaScript лишається звичайний випадний список. Статичні файли (CSS/JS) підключаються з версією за часом зміни файлу, тож після оновлення браузер не тримає застарілих стилів

**Проєкти й задачі**
- Проєкти: створення, перегляд, список, призначення відповідального, зміна статусу (активний/архівний/закритий)
- Підпроєкти — створюються кнопкою «+ Підпроєкт» на сторінці основного проєкту; показуються картками там-таки (не засмічують головний список `/projects`); задачі підпроєкту повністю окремі від задач основного проєкту. Картка проєкту в `/projects` показує кількість підпроєктів («📁 3 підпроєкти», з коректною українською формою слова), якщо вони є
- Обмеження видимості проєктів і тікетів — проєкт бачать лише автор, відповідальний, **учасники** (див. нижче) та адміністратор, тікет — заявник, призначений оператор і адміністратор; решта отримують 403 і в списку, і за прямим посиланням. Поле «Видимість» проєкту (публічний/приватний/обмежений) — лише позначка й на доступ не впливає
- **Доступ до проєкту для обраних користувачів (учасники)** — блок «🔑 Доступ до проєкту» на сторінці проєкту: автор, відповідальний (будь-якої ролі) та адміністратор додають і забирають учасників через поле з пошуком. Учасник бачить проєкт і всі його задачі в усіх розділах (списки, календар, канбан, Гант, звіти, дашборд, вкладення) і працює з ними як автор, але не керує доступом. Доступ не успадковується підпроєктами; підпроєкт без видимого основного проєкту показується в списку з позначкою «Підпроєкт · назва». Склад змін — в аудиті, лист «Вам надано доступ» — за перемикачем «Сповіщення про проєкти». SQL-правило «хто бачить проєкт» для списків, задач і дашборда зведене в одну функцію `Project::accessCondition()` (раніше було скопійоване в кількох місцях), перевірка окремої сторінки — `Project::isVisibleTo()`; без таблиці `project_members` (не виконано `update.sh`) застосунок працює як раніше й показує підказку
- Задачі: створення, перегляд, статуси, коментарі, редагування опису, призначення виконавця, перенесення в інший проєкт (основний чи підпроєкт, будь-який видимий), видалення (незворотне, каскадне)
- Канбан-дошка проєкту (і загальна по всій системі) — компактний вигляд, гнучкі колонки без горизонтальної прокрутки, перетягування картки одразу змінює статус
- Діаграма Ганта проєкту — перетягування смуги змінює дати; залежності між задачами (блокує/залежить від/пов'язана з/дублює) додаються, редагуються й видаляються прямо на сторінці
- Дорожня карта проєкту — етапи з цільовою датою, статусом і прогрес-баром на основі прив'язаних задач
- SLA для задач і проєктів — прострочені задачі (термін виконання в минулому, ще не закриті) позначаються бейджем «⚠️» на сторінці проєкту, сторінці самої задачі, обох Канбан-дошках (project + admin) і дашборді; прострочені етапи дорожньої карти — на самій дорожній карті, сторінці проєкту та в обох списках проєктів (`/projects`, `/admin/projects`). Індикатори зникають одразу після закриття задачі чи завершення етапу
- Архів (`/archive`) — закриті тікети, задачі й проєкти прибрані з головних списків (`/tickets`, `/projects`, таблиці задач на сторінці проєкту), щоб ті показували лише актуальну роботу, і зібрані окремо на цій сторінці з тими самими правилами видимості. Канбан і Гант і далі показують усі статуси, включно із закритими, — це не стосується робочих інструментів, лише оглядових списків
- Календар задач — місячна сітка, багатоденні задачі показані на початку й на завершенні

**Тікети (Service Desk, базова версія)**
- Створення звернення, список, перегляд, коментарі, зміна статусу, призначення оператора
- Необов'язкова прив'язка тікета до проєкту — видно на сторінці тікета, у загальному списку тікетів і на сторінці самого проєкту (розділ «Пов'язані тікети»)
- Черги тікетів (створення через адмін-панель)
- Портал самообслуговування (`/support`, посилання зі сторінки логіну) — подання звернення **без входу в систему**: заявник отримує персональне посилання-токен для подальшого відстеження статусу, листування з оператором і оцінки якості вирішення (CSAT, 1–5) після закриття тікета. Проста пастка для ботів (приховане поле форми) — без CAPTCHA чи інших зовнішніх залежностей
- Email-to-ticket — листи з поштової скриньки підтримки (IMAP) автоматично стають тікетами: відповіді в тій самій гілці листування додаються коментарями до наявного тікета, автовідповіді/розсилки/повідомлення про недоставку пропускаються, повторна обробка одного листа неможлива. Працює без `ext-imap` і без Composer (власний IMAP-клієнт та MIME-парсер), запускається з cron (`bin/fetch-mail.php`); підключення — у `.env`, черга й журнал обробки — в Адмін-панель → Налаштування → Пошта → тікети
- Автовідповідь заявнику (SMTP) — при створенні тікета з листа заявнику надсилається лист із посиланням для відстеження статусу; власний SMTP-клієнт (той самий підхід без залежностей, що й для IMAP), налаштування успадковує сервер/логін/пароль з IMAP, якщо не задано окремо. Домен у посиланнях (`Адмін-панель → Налаштування → Пошта → тікети → «Домен застосунку»`) можна задати прямо в інтерфейсі — без цього посилання вели б на `APP_URL` з `.env` (типово `http://localhost`)
- Email-сповіщення про активність — тікети (нова відповідь, зміна статусу — сповіщається «інша сторона», не сам автор дії), проєкти й задачі (створення з відповідальним/виконавцем, зміна призначення — лише якщо воно справді змінилось), нагадування про термін виконання задачі (за 2 дні, за 1 день, у день настання — окремий cron, `bin/send-reminders.php`). Вмикаються чотирма незалежними перемикачами (тікети / проєкти / задачі / нагадування). Кожна невдала спроба надсилання (SMTP недоступний тощо) фіксується в журналі аудиту з адресою й причиною, а не губиться мовчки
- Видимість черги непризначених тікетів — оператор служби підтримки й керівник ІТ-підрозділу бачать у `/tickets` і на сторінці «Архів» не лише свої тікети, а й усі ще нікому не призначені (бейдж «Непризначено»), щоб було з чого обирати роботу; звичайного заявника це не стосується
- SLA-ескалація для тікетів — прострочення нормативів першої відповіді й вирішення (на основі `sla_policies` для черги) позначаються бейджем у списку тікетів (прострочені піднімаються вгору списку) і детально на сторінці самого тікета та на публічній сторінці відстеження; закритий тікет прострочення не показує. Нормативи (хвилини на першу відповідь і на вирішення) налаштовуються для кожної черги в Адмін-панель → Керування → Черги тікетів, зміни фіксуються в журналі аудиту
- Оцінка якості (CSAT, 1–5) — не лише на порталі, а й для залогінених заявників на сторінці їхнього тікета (після статусу «Вирішено»/«Закрито», один раз, лише сам заявник — оператор і адміністратор оцінку лише бачать). Зведений звіт — `/admin/csat`: середня оцінка, розподіл 1–5, розбивка по чергах і операторах, останні оцінки
- Автопризначення оператора для черги — у Адмін-панель → Керування → Черги тікетів для кожної черги можна вказати оператора, який одразу призначається на кожен новий тікет у ній; працює однаково для звичайної форми, порталу самообслуговування й email-to-ticket

**Вкладення та вікі**
- Вкладення до тікетів і задач (JPG, PNG, PDF) — блок «Вкладення» на сторінці тікета й задачі: кілька файлів за раз, мініатюри зображень (зменшені копії створюються при завантаженні й для вкладень з листів, віддаються через `/attachments/ID?thumb=1`; для раніше завантажених — створюються при першому перегляді; у блоці «Вкладення» вони 120 px), завантаження, видалення (автор вкладення або адміністратор). Права успадковуються від тікета/задачі: хто бачить запис, той бачить і файли. Тип файлу визначається за **вмістом** (сигнатура та розбір зображення), а не за розширенням чи MIME від браузера; розширення має збігатися з вмістом; SVG та інші формати не приймаються. Файли лежать у `storage/uploads` **поза веб-коренем** під випадковими іменами й віддаються лише через контролер з перевіркою прав. Ліміти: 10 МБ на файл (`ATTACHMENT_MAX_MB` у `.env`), 10 файлів за раз, 30 на тікет чи задачу; реальна стеля — менше з цього та PHP-параметрів `upload_max_filesize` і `post_max_size` (інтерфейс показує значення, що діє). Файли видаляються з диска разом із задачею чи проєктом
- Зображення (PNG/JPG) під час **створення** тікета — у формі для співробітників і на порталі самообслуговування; скриншот можна **вставити з буфера обміну** (`Ctrl+V`), список вибраного показує мініатюри й дозволяє прибрати зайве. Для анонімного порталу ліміти суворіші (3 файли до 5 МБ) і є вимикач `ATTACHMENT_PORTAL_ENABLED=false`
- Зображення з вхідних листів (email-to-ticket) — PNG/JPG-вкладення **й картинки, вставлені прямо в текст листа** (Gmail, Outlook, Apple Mail) зберігаються як вкладення тікета, так само для відповідей у гілці. Вбудовані зображення менші за 10 КБ (логотипи й іконки в підписах) та дублікати відсіюються, підробки відхиляються за вмістом, до 10 картинок з одного листа. Інші типи вкладень (PDF, документи, GIF) не зберігаються — у тікеті лишається примітка з їх назвами
- Вікі (`/wiki`) — сторінки в Markdown з історією версій і відновленням, змістом, пошуком, посиланнями між сторінками (`[[адреса]]`), попереднім переглядом у редакторі та виявленням одночасних правок (другий, хто зберігає «поверх», отримує повідомлення про конфлікт і нічого не затирає). Видимість сторінки: усі / персонал (усі, крім заявників) / лише адміністратор. Створюють і редагують `admin` та `it_manager`, видаляє `admin`. Гайди (`docs/USER_GUIDE.md`, `ADMIN_GUIDE.md`, `API_GUIDE.md`) завантажуються у вікі автоматично (`bin/import-wiki-docs.php`) і оновлюються при оновленні системи, якщо їх не правили вручну. **Ієрархія сторінок** (батьківська сторінка, дерево в меню, «хлібні крихти», список підсторінок; до 6 рівнів; при видаленні сторінки її підсторінки піднімаються на рівень вище; видимість не успадковується, а назви прихованих батьків не розкриваються) та **зображення й вкладення** (JPG/PNG показуються в тексті записом `![опис](file:N)`, інші файли — `[текст](file:N)`; завантаження кнопкою, перетягуванням чи вставкою зі скриншота з буфера без перезавантаження редактора; файли лежать у `storage/uploads` і віддаються з перевіркою видимості сторінки; запис діє лише на сторінці-власниці файлу). Рендерер Markdown власний, без залежностей: HTML у тексті показується буквально, небезпечні посилання (`javascript:` тощо) не стають посиланнями, зовнішні зображення не завантажуються
- **Бібліотека документів** (`/library`, меню «Документи») — спільні файли, не прив'язані до тікета чи задачі (регламенти, інструкції, форми): розділи, пошук, **версії** документа (нові редакції не затирають старі, усі доступні для завантаження), видимість документа (усі / персонал / лише адміністратор; недоступний документ відповідає 404). Формати: PDF, JPG, PNG, DOCX, XLSX, PPTX, ODT, ODS, ODP, TXT, CSV — тип перевіряється за вмістом, файли з макросами, архіви й HTML відхиляються. Ліміт файлу — 25 МБ (`LIBRARY_MAX_MB`). Завантажують `admin` та `it_manager`, читають усі
- **Форум** (`/forum`, меню «Форум») — розділи → теми → повідомлення в Markdown; видимість розділу (усі / персонал / лише адміністратор), закріплення, закриття й перенесення тем, модерація (`admin`, `it_manager`), редагування й видалення власних повідомлень, пошук, підписка на розділ із email-сповіщенням про нові теми (кнопка на сторінці розділу, таблиця `forum_board_subscriptions`), захист від флуду (10 публікацій за 5 хвилин, 100 за добу на користувача). **Email-сповіщення про відповіді** автору теми й учасникам обговорення — окремий перемикач на сторінці «Пошта → тікети»

**REST API та вебхуки**
- **REST API `/api/v1`** (за замовчуванням вимкнене; вмикається в Адмін-панель → Налаштування → API) — проєкти, задачі, тікети: читання зі списками, фільтрами й пагінацією; створення тікетів і задач; зміна статусу, виконавця й оператора (`PATCH`); коментарі; довідники. JSON, єдиний формат помилок із машинними кодами (`validation_failed`, `rate_limited`…). Запит або застосовується цілком, або не застосовується зовсім; значення, що не змінились, нічого не пишуть в аудит. Повний довідник — `docs/API_GUIDE.md`
- **Токени доступу** — персональні (у профілі користувача) і для службових облікових записів інтеграцій (створює адміністратор). У БД лежить лише SHA-256 токена, повний токен показується один раз; права «лише читання» чи «читання й запис», необов'язковий термін дії, відкликання, до 20 діючих на користувача. Токен діє **з правами власника і з тією самою видимістю, що й у вебі** (єдині правила в `App\Core\Access` та моделях); запис без доступу відповідає 404. Сесії й cookie API ігнорує, тож міжсайтова підробка запиту неможлива. Обмеження частоти на токен (120 запитів/хв за замовчуванням, змінюється), дії через API позначаються в журналі аудиту («Через: api»)
- **Вебхуки** — система сама надсилає події (17 подій: створення, статуси, призначення й коментарі тікетів; задачі; проєкти й доступ учасників) на адреси, які налаштовує адміністратор (Адмін-панель → Налаштування → Вебхуки). Кожен запит підписаний HMAC-SHA256 (разом із міткою часу — захист від відтворення); подія записується в чергу в одній транзакції зі зміною (відкат скасовує й подію); повтори через 1 хв, 5 хв, 30 хв, 2 год, 12 год; автовимкнення після 20 невдач поспіль; журнал доставок із ручним повтором; тестова подія; захист від SSRF (адреса перевіряється перед відправкою, з'єднання на перевірену IP, без перенаправлень, link-local заборонено завжди). Нові події відправляються після відповіді користувачу (PHP-FPM) або cron-скриптом `bin/deliver-webhooks.php`

**Облік часу та звітність**
- Облік часу на задачі — години, дата, категорія, історія записів
- Зведений облік часу проєкту — розбивка по днях/тижнях/місяцях і по учасниках; години підпроєкту рахуються як частина основного проєкту в загальних звітах адміністратора, не окремим рядком
- PDF-звіти (`/reports`) — фільтри за проєктом/користувачем/періодом/категорією (фільтр за проєктом автоматично включає його підпроєкти), діаграма розподілу годин по користувачах, таблиця згрупована по проєктах

**Загальносистемні інструменти адміністратора** (`/admin`, лише роль `admin`)
- Канбан-дошка, діаграма Ганта, облік часу та журнал аудиту по всіх проєктах одразу
- Керування користувачами (створення, редагування, зміна пароля, активація/деактивація, зняття блокування, видалення за відсутності пов'язаних даних); список розділено на локальні акаунти й акаунти Active Directory, а AD-акаунти ще й згруповано за організаційними підрозділами (OU)
- Керування проєктами (перегляд усіх, зміна видимості й статусу, незворотне видалення)
- Налаштування безпеки входу (`/admin/security`)
- Керування чергами тікетів: створення, SLA-нормативи, автопризначення оператора
- Active Directory (`/admin/ad`): підключення, перевірка з'єднання, синхронізація, відповідність груп ролям
- Звіт CSAT (`/admin/csat`)

Уже зроблено й більше не є планами (версія 0.2.3): роль «Адміністратор Підрозділу»; мініатюри вкладень і власні вкладення анонімного заявника; форум — сповіщення про нові теми (підписка на розділ), позначки «непрочитане», вкладення в повідомленнях і попередній перегляд Markdown; прибране поле «Видимість» проєкту.

## Вимоги до сервера

- PHP 8.1+ (розроблено та перевірено на 8.3) з розширенням `pdo_mysql`
- MySQL 8.x або MariaDB 10.6+
- Apache (з `mod_php` або `mod_proxy_fcgi`) або Nginx + PHP-FPM
- Контейнеризація не використовується (класичне розгортання на ОС)
- Для email-to-ticket (необов'язково): доступ сервера до IMAP-скриньки, розширення `openssl` (для SSL/STARTTLS) і `cron` для `bin/fetch-mail.php`
- Для автовідповіді та email-сповіщень (необов'язково, потребує вже налаштованого email-to-ticket): доступ сервера до SMTP-сервера (може бути той самий, що й для IMAP) і `cron` для `bin/send-reminders.php` (нагадування про термін)
- Для вкладень: каталог `storage/uploads` з правом запису для веб-сервера та PHP-параметри `upload_max_filesize` і `post_max_size`, не менші за потрібний ліміт файлу. **За замовчуванням PHP дозволяє лише 2 МБ на файл** — щоб приймати до 10 МБ, збільште обидва в `php.ini` вашого PHP-FPM/Apache і перезапустіть його (`update.sh` і `install.sh` показують поточні значення). Розширення `fileinfo` для вкладень **не потрібне**; розширення GD (`php8.3-gd`) — **необов'язкове**: з ним для зображень створюються мініатюри (320 px), без нього вкладення працюють, але список показує повні файли. Ті самі каталог і PHP-ліміти використовують бібліотека документів (до 25 МБ на файл, `LIBRARY_MAX_MB`) і вкладення вікі; розширення PHP `zip` не потрібне (структуру docx/xlsx/pptx/odt система перевіряє сама)
- Для вебхуків: cron щохвилини — `php /шлях/до/itsm-system/bin/deliver-webhooks.php` (виконує повтори невдалих доставок; на Apache з `mod_php`, без PHP-FPM, потрібен і для самих нових подій). Для REST API на Apache із PHP-FPM потрібне правило пересилання заголовка `Authorization` — воно вже є в `public/.htaccess`
- Для Active Directory (необов'язково): розширення PHP `ldap` (`apt install php-ldap`), доступ сервера до контролера домену (порт 389 або 636) і `cron` для `bin/sync-ad-users.php`

## Оновлення вже розгорнутої системи

Якщо система вже встановлена і потрібно лише накотити нові файли/виправлення, використовуйте `update.sh` — окремий скрипт, який **не питає пароль БД повторно** (читає його з вашого існуючого `.env`):

```bash
# 1. Скопіюйте оновлені файли поверх старих (окрім .env — його не чіпайте)
# 2. Потім одна команда:
sudo bash update.sh
```

Скрипт послідовно перевіряє й, за потреби, виправляє: кодування кирилиці, колонку «відповідальний за проєкт», колонку «дата початку задачі», таблицю етапів дорожньої карти, індекси для звітів обліку часу й журналу аудиту, таблицю/колонки для блокування входу, колонку прив'язки тікета до проєкту, колонку токена доступу для порталу самообслуговування, унікальність SLA-нормативу на чергу, таблицю журналу обробки пошти, налаштування автовідповіді заявнику, таблицю нагадувань про термін, гранульовані перемикачі email-сповіщень, колонку автопризначення оператора для черги, колонки й таблицю для Active Directory (AD-логін, OU, відповідність груп ролям), таблицю вкладень та директорію `storage/uploads` (з правами 660/770 для завантажених файлів), колонку джерела вкладення, таблиці вікі разом із завантаженням у неї гайдів з `docs/`, таблицю учасників проєктів, таблиці REST API й вебхуків (API за замовчуванням вимкнене), таблицю лічильників обмеження частоти запитів, таблиці бібліотеки документів і форуму, колонку батьківської сторінки й таблицю вкладень вікі, каталог `storage/logs` для журналу помилок, застарілий кеш шрифтів PDF-звітів, і насамкінець — права доступу до файлів. Безпечний для повторного запуску — якщо виправляти нічого, просто про це повідомить.

## Розгортання (первинна інсталяція)

### Варіант А — автоматична інсталяція (рекомендовано)

Скрипт `install.sh` перевіряє всі залежності, створює БД і користувача, застосовує схему та генерує `.env`:

```bash
chmod +x install.sh

# Спершу — тільки перевірка, без жодних змін у системі:
./install.sh --check-only

# Повна інсталяція:
sudo ./install.sh

# Якщо БД уже створена і потрібна лише перевірка середовища:
sudo ./install.sh --skip-db
```

Що перевіряє скрипт:
- версію PHP (мінімум 8.1) та обов'язкові розширення (`pdo`, `pdo_mysql`, `mbstring`, `json`, `session`);
- опційні розширення (`ldap` для AD-інтеграції, `openssl` та `iconv` для пошти) — попередження, не помилка;
- поточні `upload_max_filesize` і `post_max_size` PHP — це стеля розміру вкладень (CLI-налаштування можуть відрізнятися від PHP-FPM/Apache, тому це орієнтир);
- наявність і доступність MySQL/MariaDB;
- наявність веб-сервера (Nginx + PHP-FPM або Apache);
- цілісність структури проєкту та синтаксис усіх PHP-файлів;
- **власника та права доступу файлів** — автоматично визначає користувача веб-сервера
  (`www-data`/`apache`/`nginx`/`_www` залежно від ОС) і виставляє: директорії 750,
  файли 640, `storage/uploads` та кеш шрифтів PDF 770, `.env` 600.

Додаткові прапорці:
- `--skip-perms` — не чіпати власника/права файлів (якщо керуєте цим окремо, наприклад Ansible/Puppet);
- `--web-user=ІМ_'Я` — задати користувача веб-сервера вручну, якщо автовизначення не підійшло.

За наявності критичних помилок інсталяція зупиняється з ненульовим кодом виходу і підказками щодо встановлення відсутніх пакетів для вашої ОС (Debian/Ubuntu, RHEL/Rocky/Alma, macOS).

### Варіант Б — ручне розгортання

1. Скопіювати проєкт на сервер, наприклад у `/var/www/itsm-system`.
2. Налаштувати веб-сервер так, щоб **document root вказував на папку `public/`** (не на корінь проєкту!).
3. Створити базу даних і застосувати схему:
   ```bash
   mysql -u root -p -e "CREATE DATABASE itsm CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;"
   mysql --default-character-set=utf8mb4 -u root -p itsm < database/schema.sql
   mysql --default-character-set=utf8mb4 -u root -p itsm < database/seed.sql
   ```
   ⚠️ **Прапорець `--default-character-set=utf8mb4` обов'язковий.** Без нього клієнт `mysql`
   може прочитати файл в іншому кодуванні (типово latin1) і записати кирилицю з `seed.sql`
   у БД пошкодженою — подвійно перекодованою (див. розділ «Усунення несправностей» нижче).

   Файли `schema.sql` / `seed.sql` не містять `CREATE DATABASE` та `USE`, тому назва БД
   задається аргументом команди — можна розгорнути кілька інстансів (test/prod) з тих самих файлів.
4. Створити окремого користувача БД для застосунку (не root):
   ```sql
   CREATE USER 'itsm_user'@'localhost' IDENTIFIED BY 'надійний_пароль';
   GRANT ALL PRIVILEGES ON itsm.* TO 'itsm_user'@'localhost';
   FLUSH PRIVILEGES;
   ```
5. Файл `.env` (створюється автоматично `install.sh`, або скопіюйте вручну з прикладу нижче) зчитується застосунком самостійно — **жодних додаткових `SetEnv`/`env[]` у конфігурації Apache чи PHP-FPM не потрібно**:
   ```
   DB_HOST=127.0.0.1
   DB_DATABASE=itsm
   DB_USERNAME=itsm_user
   DB_PASSWORD=надійний_пароль
   APP_ENV=production
   APP_URL=https://itsm.example.local
   ```
   Головне — щоб файл `.env` лежав у корені проєкту (поруч із `app/`, `public/`, `config/`) і був читабельний користувачем, від імені якого працює веб-сервер (`www-data`, `apache` тощо).
6. Переконатися, що папки `storage/uploads` та `app/Vendor/tfpdf/font/unifont` доступні для запису веб-сервером (перша — для файлів вкладень, друга — для кешу метрик шрифтів PDF-звітів).
7. Виставити власника і права доступу. Найпростіше — викликати лише відповідну частину `install.sh`:
   ```bash
   sudo ./install.sh --skip-db --web-user=www-data
   ```
   Або вручну:
   ```bash
   sudo chown -R www-data:www-data /var/www/itsm-system
   sudo find /var/www/itsm-system -type d -exec chmod 750 {} \;
   sudo find /var/www/itsm-system -type f -exec chmod 640 {} \;
   sudo chmod 770 /var/www/itsm-system/storage/uploads
   sudo chmod 770 /var/www/itsm-system/app/Vendor/tfpdf/font/unifont
   sudo chmod 600 /var/www/itsm-system/.env
   ```
8. Обов'язково змінити пароль тестового адміністратора (`admin@example.local` / `admin123`) або видалити цей рядок із `seed.sql` перед продуктивним використанням.

## Безпека

Що вже реалізовано:
- **Розмежування доступу до проєктів і тікетів** — непричетний користувач не бачить проєкт чи тікет ні в списку, ні за прямим посиланням (HTTP 403), так само для задач усередині недоступного проєкту. Адміністратор системи бачить усе завжди.
- **CSRF-захист** на всіх формах — токен генерується на сесію (`App\Core\Csrf`) і перевіряється централізовано в `App\Core\Router::dispatch()` для кожного POST-запиту.
- **Захист від session fixation** — `session_regenerate_id()` одразу після успішного логіну.
- **Блокування облікового запису після невдалих спроб входу** (`/admin/security`) — кількість спроб і тривалість блокування налаштовуються через інтерфейс; блокування прив'язане до конкретного користувача.
- **Валідація значень, обмежених переліком** — видимість проєкту, пріоритет і тип задачі, статус тікета перевіряються проти білого списку до звернення до БД.
- **Паролі** — хешуються `password_hash()` (bcrypt), мінімум 8 символів.
- **XSS** — увесь вивід даних користувача проходить через `View::e()` (`htmlspecialchars`).
- **SQL-ін'єкції** — усі запити через підготовлені вирази (PDO prepared statements).
- **Портал самообслуговування** (`/support`) — токен доступу для анонімного відстеження генерується криптографічно стійким генератором (`random_bytes`, 48 hex-символів — практично неможливо підібрати перебором), і в самій формі подання є найпростіша пастка для ботів (приховане поле, яке бачать лише автоматичні скрипти).
- **Email-to-ticket** — пароль скриньки лежить лише в `.env` (не в БД) і ніколи не передається в шаблони чи показується в інтерфейсі; лист перетворюється на простий текст (HTML не зберігається — поверхні для XSS немає); коментар до чужого тікета за міткою `[#123]` у темі приймається лише від заявника цього тікета (номер легко вгадати); лист від «оператора» завжди записується як коментар заявника, тож підроблений `From` не може вплинути на SLA; зберігаються лише зображення PNG/JPG і лише після перевірки вмісту (підробки відхиляються), решта вкладень не зберігається й не виконується.
- **Автовідповідь і email-сповіщення** — пароль SMTP так само лише в `.env`; заголовки `Auto-Submitted`/`X-Auto-Response-Suppress` у вихідних листах запобігають циклу автовідповідей із зовнішніми поштовими системами; збій надсилання (SMTP недоступний, невірний пароль тощо) ніколи не зриває дію, яка його спричинила (тікет/проєкт/задача все одно створюються чи оновлюються), а фіксується в журналі аудиту з адресою одержувача й причиною — не губиться мовчки.
- **Active Directory** — службовий обліковий запис потрібен лише для читання каталогу (не адміністратор домену); сам вхід — окремий bind як сам користувач, пароль ніде не зберігається; ім'я користувача підставляється в LDAP-фільтр з екрануванням спецсимволів (RFC 4515) — логін на кшталт `*)(uid=*` не підміняє фільтр; порожній пароль відхиляється явно (за специфікацією LDAP він означає анонімний bind і сервер повернув би «успіх»); локальні облікові записи ніколи не перехоплюються через збіг email з AD-записом; пароль службового акаунта лише в `.env`, ніколи не підставляється назад у форму й не потрапляє в журнал аудиту. Пошук у каталозі постраничний (обмеження AD у 1000 записів на запит не діє); якщо сервер усе ж віддав неповний результат, синхронізація скасовується з помилкою й **нікого не деактивує** — вона не діє на підставі неповних даних. Відсутнє розширення `ldap` дає зрозуміле повідомлення адміністратору, а не помилку 500.
- **Запис `.env` з веб-форми** (`/admin/ad`) — доступний лише адміністратору; запис атомарний (тимчасовий файл + rename), решта файлу не змінюється. Щоб форма працювала, процес веб-сервера має мати право запису в `.env`, а `install.sh` за замовчуванням видає `600` власнику-інсталятору. Надати право запису — свідомий компроміс (файл містить і пароль БД); альтернатива — лишити права як є й редагувати `.env` вручну. Якщо запису немає, форма покаже точну команду для виправлення.
- **Content-Security-Policy** — `script-src` суворий (nonce, без `unsafe-inline`), тож впроваджений у сторінку чужий `<script>` або обробник `onclick=` не виконається. `style-src` лишає `'unsafe-inline'` (кілька динамічних інлайн-стилів, наприклад смужки прогресу) — ризик значно нижчий, ніж для скриптів. Дозволені CDN (`jsdelivr.net`, `cdnjs.cloudflare.com`) прописані в `App\Core\Csp`; підключення іншого CDN чи власного дзеркала вимагає правки цього класу.
- **Вкладення** — файли лежать у `storage/uploads` **поза веб-коренем** (`public/`), тож прямого URL на них немає: віддаються лише контролером, який кожного разу перевіряє права на тікет чи задачу. Імена на диску — випадкові 32 hex-символи без жодної частини від користувача (обхід директорій і підміна розширення неможливі), оригінальна назва лишається лише в БД і перед показом очищається від шляхів, керувальних символів і символів зміни напрямку тексту. Тип визначається за **вмістом**, а не за розширенням чи MIME від браузера; PHP під виглядом `.jpg` відхиляється. Заголовок `Content-Disposition` будується з ASCII-варіантом і `filename*` (лапки чи `;` в імені його не ламають), відповідь має `X-Content-Type-Options: nosniff`. Вміст файлу ніколи не виконується, а SVG та інші формати, що можуть нести скрипти, не дозволені взагалі.
- **Вікі / Markdown** — увесь текст сторінки екранується (`htmlspecialchars`), HTML утворюють лише самі конструкції рендерера; сирий HTML у тексті показується буквально. Посилання проходять білий список (`http`, `https`, `mailto`, відносні `/…` та `#якорі`), тож `javascript:`, `data:`, `vbscript:` і `//host` не стають посиланнями; зображення не підтримуються. Службові символи, якими рендерер позначає проміжні вставки, вилучаються з вхідного тексту, тож їх не можна підробити. Глибина вкладеності обмежена, а збій регулярного виразу дає екранований текст, а не помилку. Сторінка, до якої в користувача немає доступу, відповідає 404 (не видно навіть її існування).
- **Журнал помилок** — у `storage/logs` (поза веб-коренем) пишуться лише код, місце й текст помилки та стек без аргументів: тіло запиту (паролі форми входу), рядок запиту й абсолютні шляхи сервера не потрапляють у файл. Технічні подробиці на сторінці помилки бачить лише адміністратор (за роллю, а не за `APP_ENV`, який за замовчуванням `local`); інші — тільки код інциденту.
- **REST API** — автентифікація лише токеном у заголовку (запасний — `X-Api-Token`; токен в адресі запиту не приймається, бо потрапляє в логи). У БД лише хеш токена, повний токен показується один раз; відкликаний, прострочений, неіснуючий і токен деактивованого власника дають **однакову** відповідь 401 (не видно причини). Права токена — рівно права власника, зміна ролі діє негайно. Cookie/сесії API не читає й не створює (`Set-Cookie` немає), CSRF-перевірку для `/api` замінює токен: міжсайтовий запит не може додати заголовок `Authorization`, а `Content-Type: application/json` вимагає попереднього запиту CORS, якого сервер не дозволяє. Ліміт запитів на токен, обмеження тіла 1 МБ, суворі перевірки полів.
- **Вебхуки** — підпис HMAC-SHA256 від `мітка_часу.тіло`; секрет зберігається в БД відкрито (потрібен для підпису) й показується лише при створенні й заміні, керує ним лише адміністратор. Захист від **SSRF**: дозволені лише `http`/`https` без логіна в адресі; ім'я хоста розпізнається й перевіряється **до** відправки, а з'єднання йде на вже перевірену IP (підміна DNS між перевіркою й запитом не діє); перенаправлення не виконуються; адреси link-local (`169.254.0.0/16`, метадані хмарних серверів), службові й мультикаст заборонені завжди, внутрішні (10/8, 172.16/12, 192.168/16, 127/8) — за замовчуванням дозволені, а `WEBHOOK_ALLOW_PRIVATE=false` у `.env` забороняє їх. **Увага:** події містять дані тікетів і задач (теми, описи, email заявників) і надсилаються незалежно від прав окремих користувачів — створюйте вебхуки лише на довірені адреси.

Відомі обмеження (свідомо поза межами MVP, див. «Наступні кроки розробки»):
- **Email-to-ticket не перевіряє справжність відправника** (SPF/DKIM не аналізуються): будь-хто може написати листа з адресою співробітника, і тікет буде прив'язано до його облікового запису. Покладайтесь на антиспам-фільтрацію та SPF/DKIM-перевірку на самому поштовому сервері перед скринькою підтримки.
- **Обмеження частоти запитів порталу `/support`** є (за IP; налаштування — `config/config.php`, `PORTAL_RATE_LIMIT`, `TRUSTED_PROXIES`), але це фіксоване вікно з лічильником у БД, а не захист від розподіленого спаму з багатьох адрес. **За проксі/балансувальником обов'язково вкажіть його адресу в `TRUSTED_PROXIES`**, інакше всі відвідувачі ділитимуть один ліміт. Файли від анонімів і далі обмежені (3 файли до 5 МБ за звернення); на порталі в інтернеті їх можна вимкнути: `ATTACHMENT_PORTAL_ENABLED=false`.
- Загальний розмір листа в email-to-ticket обмежений 10 МБ — листи з кількома великими фото можуть його перевищити й будуть пропущені (з записом у журналі обробки).
- Сесії зберігаються файлово — для кількох веб-серверів за балансувальником знадобиться спільне сховище.
- **Bootstrap і Frappe Gantt** підключені з CDN (`jsdelivr.net`, `cdnjs.cloudflare.com`) — потрібен доступ сервера/браузера до інтернету. Якщо мережа повністю ізольована — верстка Bootstrap та сторінка `/gantt` не завантажаться, решта функціоналу не постраждає.
- **PDF-звіти працюють повністю офлайн** — бібліотека tFPDF (LGPL) і шрифт DejaVu Sans вбудовані у файли проєкту (`app/Vendor/tfpdf/`), без Composer і без звернень до інтернету.

## Усунення несправностей

**HTTP 419 "Сесія застаріла" при відправленні форми.**
Це CSRF-захист — токен форми не збігається з токеном поточної сесії. Типові причини: форму тримали відкритою дуже довго в іншій вкладці; користувача розлогінило поки форма була відкрита; форму надіслано повторно з кешованої сторінки. Рішення — оновити сторінку (F5) і заповнити форму заново.

**Порожня сторінка / 500 після входу.**
Найімовірніша причина — застосунок не може підключитися до БД. Перевірити:
```bash
sudo -u www-data php -r "print_r(require '/шлях/до/itsm-system/config/config.php');"
```
Якщо `.env` не знайдено — конфіг покаже дефолтні значення, і саме тому не з'єднається з реальною БД. Деталі помилки — в лозі PHP/Apache: `tail -f /var/log/apache2/error.log` або `tail -f /var/log/php-fpm/*.log`.

**Замість сторінки — «Сталася внутрішня помилка» з кодом (помилка 500).**
Це не порожня 500, а сторінка самого застосунку: увійдіть **адміністратором** і відкрийте ту саму сторінку — вона покаже причину (клас, текст помилки, `файл:рядок`). Повний запис зі стеком — у `storage/logs/app-РРРР-ММ-ДД.log`, шукайте код: `grep КОД storage/logs/*.log`. Найчастіші причини: не запускали `update.sh` (`Table '…' doesn't exist`); після копіювання файлів PHP-FPM лишив у пам'яті старий код (opcache) — `sudo systemctl reload php8.3-fpm` (ім'я залежить від версії); немає прав на `storage` — `sudo bash update.sh`. Повна таблиця причин — `docs/ADMIN_GUIDE.md`, розділ 17. Якщо ж сторінка помилки не з'являється й видно порожню «HTTP 500», збій стався до запуску застосунку — дивіться лог веб-сервера (див. вище).

**Apache: "Not Found" на будь-якому URL, крім `/`.**
Не спрацьовує `.htaccess`:
```bash
sudo a2enmod rewrite && sudo systemctl restart apache2
```
і перевірте, що для директорії `public/` виставлено `AllowOverride All`.

**Nginx: 404 на всіх URL, крім `/`.**
Nginx не читає `.htaccess` — маршрутизацію потрібно прописати в конфізі:
```nginx
location / {
    try_files $uri $uri/ /index.php?$query_string;
}
```

**Назви ролей, типів задач, статусів виглядають як "кракозябра".**
Наслідок подвійного UTF-8-кодування при застосуванні `seed.sql` без прапорця `--default-character-set=utf8mb4`. Найпростіше виправлення:
```bash
sudo bash update.sh
```
Або вручну:
```bash
mysql -u root -p --default-character-set=utf8mb4 ІМ_Я_БД < database/migrations/002_fix_utf8_double_encoding.sql
```

**AD-користувач не може увійти: «Невірний email або пароль».**
Це свідомо узагальнене повідомлення — воно однаково з'являється, коли акаунта ще немає локально, і коли пароль невірний. Найчастіша причина — синхронізація ще не створила обліковий запис: у Адмін-панель → Налаштування → Active Directory натисніть «Синхронізувати зараз» і перевірте, що користувач з'явився на сторінці «Користувачі» у розділі Active Directory. Вхід відбувається за **email** з цього запису (не за AD-логіном). Докладніше — у `docs/ADMIN_GUIDE.md`, розділ 12.

**На сторінці Active Directory: «Розширення PHP «ldap» не встановлено».**
```bash
sudo apt install php-ldap
sudo systemctl restart php8.3-fpm    # або apache2 — залежно від вашого розгортання
```

**Вкладення не завантажується: «файл перевищує ліміт сервера» або «Файли завеликі: сумарний розмір запиту перевищує ліміт».**
Це ліміти самого PHP (`upload_max_filesize` — на файл, `post_max_size` — на весь запит; за замовчуванням 2 МБ і 8 МБ), а не застосунку (він дозволяє до 10 МБ). Збільште обидва в `php.ini` вашого PHP-FPM/Apache (`upload_max_filesize = 12M`, `post_max_size = 40M`) і перезапустіть його; у формі завантаження написано, яка стеля діє зараз. Окрім PHP, Nginx має власний ліміт — `client_max_body_size`.

**Вкладення: «не вдалося зберегти файл на сервері».**
Веб-сервер не має права запису в `storage/uploads`. Виправлення: `sudo chmod 770 storage/uploads && sudo chown -R www-data:www-data storage/uploads` (або `sudo bash update.sh`, який виставляє права сам).

**Лист із картинками не став тікетом або картинки не збереглися.**
Дивіться журнал обробки пошти (Адмін-панель → Налаштування → Пошта → тікети): у ньому причина й кількість збережених зображень. Найчастіше: лист понад 10 МБ загалом (пропускається цілком); картинка не PNG/JPG (GIF, WebP тощо не зберігаються — вони названі в описі тікета); вбудована картинка менша за 10 КБ (вважається логотипом підпису й свідомо пропускається).

**Після оновлення сторінка виглядає по-старому або поле пошуку виконавця «подвоїлось».**
Раніше браузер міг тримати застарілий `app.css`. Тепер CSS і JS підключаються з версією за часом зміни файлу (`?v=…`), тож це трапляється лише якщо оновлено не всі файли — переконайтеся, що скопійовано всю папку `public/assets/`.

**REST API: `401 unauthenticated`, хоча токен правильний.**
Перевірте стан токена в Адмін-панель → Налаштування → API (відкликаний, прострочений, власника деактивовано дають однакову відповідь 401). Якщо токен діє, а 401 лишається, веб-сервер, імовірно, не передає заголовок `Authorization` у PHP: на Apache із PHP-FPM/CGI потрібне правило `RewriteRule .* - [E=HTTP_AUTHORIZATION:%{HTTP:Authorization}]` (воно є в `public/.htaccess`, але не діє, якщо `AllowOverride None` — тоді додайте його у віртуальний хост); альтернатива — передавати токен заголовком `X-Api-Token`.

**REST API: `503 api_disabled` або `api_unavailable`.**
`api_disabled` — API вимкнене (Адмін-панель → Налаштування → API → «Увімкнути REST API»). `api_unavailable` — не виконано `update.sh` (немає таблиць API).

**Вебхуки не доходять.**
Адмін-панель → Налаштування → Вебхуки: чи вебхук активний (його могло вимкнути автоматично — причина в списку) і чи підписаний на потрібну подію; «журнал» показує код відповіді й текст помилки кожної спроби; кнопка «Надіслати тестову подію» перевіряє канал і підпис. Без PHP-FPM (Apache `mod_php`) нові події лишаються в черзі, доки не працює cron `bin/deliver-webhooks.php` — сторінка вебхуків попереджає, якщо планувальник мовчить. Типові причини збою: адреса за `WEBHOOK_ALLOW_PRIVATE=false` чи link-local, самопідписаний сертифікат одержувача (знімається прапорцем «Перевіряти TLS-сертифікат» лише для внутрішніх сервісів), одержувач відповідає довше за 6 секунд або перенаправленням (3xx). Таблиця причин — `docs/ADMIN_GUIDE.md`, розділ 19.

**Сторінка гайда у вікі не оновилась після оновлення системи.**
Імпорт (`bin/import-wiki-docs.php`) не затирає сторінки, які редагували у вікі вручну, — він пише про це в звіті `update.sh`. Щоб перезаписати свіжою документацією (ваша версія лишиться в історії сторінки): `php bin/import-wiki-docs.php --force`.

**PDF-звіт не генерується / помилка `Can't open file ... DejaVuSans.ttf`.**
Директорія `app/Vendor/tfpdf/font/unifont` недоступна для запису веб-серверу, або в ній лишився кеш метрик шрифту з іншого сервера. Виправлення:
```bash
sudo bash update.sh
```
Або вручну:
```bash
rm -f app/Vendor/tfpdf/font/unifont/*.mtx.php app/Vendor/tfpdf/font/unifont/*.cw.dat app/Vendor/tfpdf/font/unifont/*.cw127.php
chmod 770 app/Vendor/tfpdf/font/unifont
```
