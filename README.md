# ITSM System — v0.1.0 (MVP, Епіки 1–3, 12)

Легкий PHP-застосунок (без Composer/фреймворку) для управління ІТ-проєктами, задачами та зверненнями, згідно з ТЗ v3.1. Розроблено для системних адміністраторів та керівників ІТ-підрозділу — не для команд розробки ПЗ (без інтеграції з системами контролю версій, без релізного циклу продукту).

Поточну версію застосунку видно у футері веб-інтерфейсу та у файлі `VERSION` у корені проєкту.

📘 Окремі покрокові інструкції (Markdown + Word-версії в `docs/`):
- [`docs/ADMIN_GUIDE.md`](docs/ADMIN_GUIDE.md) / `docs/ITSM_Admin_Guide.docx` — для адміністратора системи (керування користувачами, проєктами)
- [`docs/USER_GUIDE.md`](docs/USER_GUIDE.md) / `docs/ITSM_User_Guide.docx` — для звичайних користувачів (робота з проєктами, задачами, обліком часу)
- [`docs/GIT_GUIDE.md`](docs/GIT_GUIDE.md) / `docs/ITSM_Git_Guide.docx` — як ініціалізувати git та відправити проєкт на GitHub
- `docs/ITSM_System_Documentation.docx` — Word-версія цього ж README, для друку чи надсилання поштою

**Реалізовано у цій версії (Sprint 0 + MVP):**
- **Усі стилі винесено в один файл** `public/assets/css/app.css` — жодного `style="..."` у HTML-шаблонах більше немає (легше підтримувати, браузер кешує CSS окремо від HTML). Розміри (ширина контейнера, висота Канбан-колонок і рядків календаря) лишились такими самими, як і раніше, — жодних змін вигляду.
- Автентифікація (локальна, сесійна)
- Проєкти: створення, перегляд, список, **вибір/зміна відповідального (виконавця) з наявних користувачів**
- **Обмеження видимості проєктів і тікетів**: список і сторінка проєкту/тікета доступні лише автору, відповідальному/призначеному оператору та адміністратору системи — усі інші користувачі не бачать їх ні в списку, ні за прямим посиланням (403), включно із задачами всередині таких проєктів
- **Канбан-дошка проєкту** — задачі згруповані колонками за статусом, перетягування картки між колонками (drag-and-drop) миттєво змінює статус задачі; текст на картках компактний (12px), однаково на дошці проєкту й на загальній дошці всіх проєктів
- **Діаграма Ганта проєкту** — терміни задач у вигляді смуг (Frappe Gantt), перетягування/розтягування смуги миттєво зберігає нові дати початку/завершення; **залежності між задачами** (блокує / залежить від / пов'язана з / дублює) відображаються стрілками, додаються, **редагуються (зміна типу) і видаляються** прямо на сторінці діаграми; при відкритті сторінка прокручується так, щоб **«сьогодні» було зліва** (так само, як і на загальній діаграмі `/admin/gantt`)
- **Загальні Канбан-дошка, Діаграма Ганта та Облік часу по всій системі** (`/admin/board`, `/admin/gantt`, `/admin/time`, лише роль `admin`) — ті самі інструменти, але одразу з усіма проєктами на одному екрані (кожна картка/смуга позначена назвою свого проєкту), для загального огляду навантаження без переходу по кожному проєкту окремо. Картки на загальній дошці — з меншим шрифтом (щоб влізало більше без прокрутки), а загальна діаграма Ганта при відкритті прокручується так, щоб «сьогодні» було зліва (а не по центру, як типово для Frappe Gantt) — щоб одразу було видно все майбутнє навантаження. Загальний облік часу має ті самі вкладки по днях/тижнях/місяцях, але в кожній — уже **три** таблиці одразу: загальна сума, розбивка по користувачах і розбивка **по проєктах** (з посиланням на власну сторінку обліку часу кожного) — саме останньої немає на проєктній версії, бо там і так усі записи вже одного проєкту. Список «Усі записи» — під спойлером (згорнутий за замовчуванням); **клік на будь-яку дату/тиждень/місяць** у будь-якій з трьох таблиць динамічно (без перезавантаження сторінки) розгортає спойлер і показує лише записи цього періоду, з кнопкою «Скинути» для повернення до повного списку
- **Календар задач** — місячна сітка, де кожна багатоденна задача показана **лише в день початку («▶») і в день терміну виконання («◀»)** — проміжні дні не заповнюються; одноденні задачі (лише одна дата) показані один раз без стрілок, навігація по місяцях, кольорове кодування за пріоритетом, закриті задачі показані перекресленими
- **Дорожня карта проєкту** (`/projects/{id}/roadmap`, Епік 4) — етапи/контрольні точки з цільовою датою, статусом (заплановано/у процесі/завершено/затримується) і прогрес-баром на основі прив'язаних задач; задачу можна прив'язати до етапу при створенні або на сторінці задачі; створювати/видаляти етапи можуть ролі «Адміністратор системи» та «Керівник ІТ-підрозділу», змінювати статус — будь-хто з доступом до проєкту; видалення етапу не видаляє прив'язані задачі, лише знімає прив'язку
- **Зведений облік часу по проєкту** (`/projects/{id}/time`) — загальна сума годин, **розбивка по днях/тижнях (ISO 8601)/місяцях** у вигляді вкладок (у кожній — і загальна сума за період, і **та сама сума в розрізі кожного користувача**), розбивка по кожному учаснику за весь час, і повний список усіх записів по всіх задачах проєкту одразу з посиланням на кожну задачу
- **Звіти у форматі PDF** (`/reports` — доступ через кнопку «📄 Сформувати звіт» на сторінках обліку часу проєкту й усієї системи, а не через верхнє меню) — фільтрований звіт обліку часу за тиждень або місяць, з опціональними фільтрами за проєктом, користувачем і категорією активності; перехід із проєктної сторінки обліку часу попередньо обирає саме цей проєкт у формі; генерується напряму на сервері (бібліотека tFPDF, без Composer, кирилиця через вбудований шрифт DejaVu Sans), результат — файл для завантаження. У шапці звіту — горизонтальна діаграма розподілу годин по користувачах (довжина смуги пропорційна кількості годин), нижче — таблиця записів, **згрупована по проєктах**, з проміжним підсумком годин на кожен проєкт і загальною сумою внизу
- Задачі: створення, перегляд, зміна статусу, коментарі, **облік часу з історією записів** (хто, скільки годин, коли, категорія), **вибір/зміна виконавця з наявних користувачів**
- **Тікети (базова версія Service Desk)**: створення звернення, список, перегляд, коментарі (листування), зміна статусу, **призначення оператора (виконавця) з наявних користувачів**
- Рольова модель (RBAC) — базова перевірка ролей (`admin`, `it_manager` для створення проєктів)
- Журнал аудиту (audit_log) для проєктів, задач і тікетів
- **Адміністративна панель** (`/admin`, лише роль `admin`):
  - **створення нових користувачів** (ім'я, email, пароль, роль) з перевіркою унікальності email;
  - **редагування даних користувача** (ім'я, email, роль) — з захистом від зміни власної ролі;
  - зміна паролів локальних користувачів (з підтвердженням, мінімум 8 символів);
  - активація/деактивація облікових записів (крім власного);
  - **видалення користувача** — дозволено лише якщо з ним не пов'язані жодні дані
    (створені проєкти/задачі/коментарі/облік часу); якщо пов'язані дані є, система
    показує зрозуміле повідомлення і пропонує деактивацію замість видалення
    (це свідомо: видалення "зайнятого" користувача зламало б історію хто що зробив);
  - **зміна видимості проєкту** (публічний/приватний/обмежений доступ) прямо зі списку проєктів
  - перегляд усіх проєктів і **незворотне видалення проєкту** разом з усіма
    пов'язаними задачами/коментарями/вкладеннями/обліком часу (каскадно на рівні БД),
    із обов'язковим підтвердженням — потрібно ввести точну назву проєкту
  - **створення черг тікетів** (назва + опис) з перевіркою унікальності назви —
    нова черга одразу доступна у формі створення тікета
- **Захист від CSRF** на всіх формах (централізована перевірка токена в роутері) та
  валідація допустимих значень для полів на кшталт статусу/пріоритету/видимості
  (детальніше — розділ «Безпека» нижче)

**Ще не реалізовано (наступні епіки згідно з DEV_START-документом):**
- Wiki, форуми, файлові документи (Епіки 6–8)
- Портал самообслуговування для заявників без облікового запису, email-to-ticket, SLA-ескалація, CSAT (розширення Епіку 12 — зараз реалізована лише базова версія: створення/перегляд/призначення оператора для вже автентифікованих користувачів)
- Інтеграція з Active Directory (Епік 13 — точка розширення в `App\Core\Auth::attempt()`)
- Email-сповіщення, вебхуки, REST API

## Вимоги до сервера

- PHP 8.1+ (розроблено та перевірено на 8.3) з розширенням `pdo_mysql`
- MySQL 8.x або MariaDB 10.6+
- Apache (з `mod_php` або `mod_proxy_fcgi`) або Nginx + PHP-FPM
- Контейнеризація не використовується (класичне розгортання на ОС)

## Оновлення вже розгорнутої системи

Якщо система вже встановлена і потрібно лише накотити нові файли/виправлення (наприклад, фікс кирилиці, нова колонка «відповідальний за проєкт»), використовуйте `update.sh` — окремий, значно простіший скрипт, який **не питає пароль БД повторно** (читає його з вашого існуючого `.env`):

```bash
# 1. Скопіюйте оновлені файли поверх старих (окрім .env — його не чіпайте)
# 2. Потім одна команда:
sudo bash update.sh
```

Скрипт сам:
- перевіряє й, за потреби, виправляє пошкоджену кирилицю (подвійне UTF-8-кодування — типова проблема старих інсталяцій, див. розділ «Усунення несправностей»);
- накочує нову колонку `responsible_user_id` (можливість призначати відповідального за проєкт), якщо її ще немає;
- перевстановлює права доступу на файли.

Безпечний для повторного запуску — якщо виправляти нічого, просто про це повідомить.

## Розгортання (первинна інсталяція)

### Варіант А — автоматична інсталяція (рекомендовано)

Скрипт `install.sh` перевіряє всі залежності, створює БД і користувача, застосовує схему та генерує `.env`:

```bash
chmod +x install.sh

# Спершу — тільки перевірка, без жодних змін у системі:
./install.sh --check-only

# Повна інсталяція:
sudo ./install.sh

# Якщо БД уже створена і потрібна лише перевірка середовища:
sudo ./install.sh --skip-db
```

Що перевіряє скрипт:
- версію PHP (мінімум 8.1) та обов'язкові розширення (`pdo`, `pdo_mysql`, `mbstring`, `json`, `session`);
- опційні розширення (`ldap` для AD-інтеграції, `fileinfo` для вкладень) — попередження, не помилка;
- наявність і доступність MySQL/MariaDB;
- наявність веб-сервера (Nginx + PHP-FPM або Apache);
- цілісність структури проєкту та синтаксис усіх PHP-файлів;
- **власника та права доступу файлів** — автоматично визначає користувача веб-сервера
  (`www-data`/`apache`/`nginx`/`_www` залежно від ОС) і виставляє: директорії 750,
  файли 640, `storage/uploads` 770 (запис для вкладень), `.env` 600.

Додаткові прапорці:
- `--skip-perms` — не чіпати власника/права файлів (якщо керуєте цим окремо, наприклад Ansible/Puppet);
- `--web-user=ІМ_'Я` — задати користувача веб-сервера вручну, якщо автовизначення не підійшло
  (наприклад, нестандартний користувач `nginx-itsm`).

За наявності критичних помилок інсталяція зупиняється з ненульовим кодом виходу і підказками щодо встановлення відсутніх пакетів для вашої ОС (Debian/Ubuntu, RHEL/Rocky/Alma, macOS).

### Варіант Б — ручне розгортання

1. Скопіювати проєкт на сервер, наприклад у `/var/www/itsm-system`.
2. Налаштувати веб-сервер так, щоб **document root вказував на папку `public/`** (не на корінь проєкту!).
3. Створити базу даних і застосувати схему:
   ```bash
   mysql -u root -p -e "CREATE DATABASE itsm CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;"
   mysql --default-character-set=utf8mb4 -u root -p itsm < database/schema.sql
   mysql --default-character-set=utf8mb4 -u root -p itsm < database/seed.sql
   ```
   ⚠️ **Прапорець `--default-character-set=utf8mb4` обов'язковий.** Без нього клієнт `mysql`
   може прочитати файл в іншому кодуванні (типово latin1) і записати кирилицю з `seed.sql`
   (назви ролей, типів задач, статусів, ім'я тестового адміністратора) у БД пошкодженою —
   подвійно перекодованою. Помилка непомітна в самому `mysql`, але проявляється мовчазною
   «кракозяброю» в браузері. Якщо застосували файли без цього прапорця — див. розділ
   «Усунення несправностей» нижче, там є скрипт відновлення.

   Файли `schema.sql` / `seed.sql` не містять `CREATE DATABASE` та `USE`, тому назва БД
   задається аргументом команди — можна розгорнути кілька інстансів (test/prod) з тих самих файлів.
4. Створити окремого користувача БД для застосунку (не root):
   ```sql
   CREATE USER 'itsm_user'@'localhost' IDENTIFIED BY 'надійний_пароль';
   GRANT ALL PRIVILEGES ON itsm.* TO 'itsm_user'@'localhost';
   FLUSH PRIVILEGES;
   ```
5. Файл `.env` (створюється автоматично `install.sh`, або скопіюйте вручну з прикладу нижче) зчитується застосунком самостійно — **жодних додаткових `SetEnv`/`env[]` у конфігурації Apache чи PHP-FPM не потрібно**:
   ```
   DB_HOST=127.0.0.1
   DB_DATABASE=itsm
   DB_USERNAME=itsm_user
   DB_PASSWORD=надійний_пароль
   APP_ENV=production
   APP_URL=https://itsm.example.local
   ```
   Головне — щоб файл `.env` лежав у корені проєкту (поруч із `app/`, `public/`, `config/`) і був читабельний користувачем, від імені якого працює веб-сервер (`www-data`, `apache` тощо).
6. Переконатися, що папка `storage/uploads` доступна для запису веб-сервером (для майбутнього функціоналу вкладень).
7. Виставити власника і права доступу. Найпростіше — викликати лише відповідну частину `install.sh`:
   ```bash
   sudo ./install.sh --skip-db --web-user=www-data
   ```
   (пропустить кроки з БД/`.env`, лише перевірить залежності та виставить права). Або вручну:
   ```bash
   sudo chown -R www-data:www-data /var/www/itsm-system
   sudo find /var/www/itsm-system -type d -exec chmod 750 {} \;
   sudo find /var/www/itsm-system -type f -exec chmod 640 {} \;
   sudo chmod 770 /var/www/itsm-system/storage/uploads
   sudo chmod 600 /var/www/itsm-system/.env
   ```
8. Обов'язково змінити пароль тестового адміністратора (`admin@example.local` / `admin123`) або видалити цей рядок із `seed.sql` перед продуктивним використанням.

## Локальний запуск для розробки (без Apache/Nginx)

```bash
cd itsm-system
DB_HOST=127.0.0.1 DB_DATABASE=itsm DB_USERNAME=itsm_user DB_PASSWORD=change_me php -S 127.0.0.1:8000 -t public
```

Відкрити http://127.0.0.1:8000/login

## Безпека

Що вже реалізовано:
- **Розмежування доступу до проєктів і тікетів**: непричетний користувач (не автор, не відповідальний/оператор, не адміністратор) не бачить проєкт чи тікет ні в списку, ні за прямим посиланням (HTTP 403) — так само для задач усередині недоступного проєкту та дій над ними (коментарі, статус, облік часу). Адміністратор системи бачить усе завжди.
- **CSRF-захист** на всіх формах — токен генерується на сесію (`App\Core\Csrf`) і перевіряється централізовано в `App\Core\Router::dispatch()` для кожного POST-запиту, тож новий маршрут неможливо випадково лишити незахищеним. При невідповідності токена — HTTP 419 з проханням оновити сторінку (типова причина: форма була відкрита в іншій вкладці задовго до відправлення, або дію повторно надіслано зі старої закладки).
- **Захист від session fixation** — `session_regenerate_id()` одразу після успішного логіну.
- **Валідація значень, обмежених переліком** (ENUM у БД) — видимість проєкту, пріоритет і тип задачі, статус тікета перевіряються проти білого списку в контролері до звернення до БД; при некоректному значенні користувач бачить зрозуміле повідомлення замість технічної помилки.
- **Паролі** — хешуються `password_hash()` (bcrypt), мінімум 8 символів при створенні/зміні.
- **XSS** — увесь вивід даних користувача в шаблонах проходить через `View::e()` (`htmlspecialchars`).
- **SQL-ін'єкції** — усі запити до БД через підготовлені вирази (PDO prepared statements), без конкатенації користувацьких значень у SQL.

Відомі обмеження (свідомо поза межами MVP, не для продакшн без додаткового огляду):
- Немає захисту від брутфорс-атак на форму логіну (rate limiting, блокування після N невдалих спроб).
- Немає CSP (Content-Security-Policy) заголовків.
- Сесії зберігаються файлово (стандартний механізм PHP) — для кількох веб-серверів за балансувальником знадобиться спільне сховище сесій (Redis/БД).
- **Важливий наслідок обмеження видимості тікетів**: оператор служби підтримки та керівник ІТ-підрозділу (якщо не адміністратор) бачать лише тікети, де вони заявник або вже призначений оператор — вони **не можуть переглянути чергу непризначених тікетів**, щоб узяти собі роботу самостійно. Зараз призначити оператора на тікет може лише адміністратор системи (він бачить усе). Якщо потрібно, щоб оператори/керівники бачили весь пул непризначених тікетів для самостійного розбору — дайте знати, це окреме, невелике доопрацювання.
- **Потрібен доступ сервера/браузера користувача до інтернету** для Bootstrap (CSS/JS) та Frappe Gantt (діаграма Ганта) — обидва підключені з CDN (`jsdelivr.net`, `cdnjs.cloudflare.com`), а не вбудовані у файли проєкту. Якщо сервер працює в повністю ізольованій мережі без виходу назовні — верстка Bootstrap та сторінка `/gantt` не завантажаться; решта функціоналу на це не впливає.
- **PDF-звіти (`/reports`) працюють повністю офлайн**, на відміну від Bootstrap/Ганта — бібліотека **tFPDF** (LGPL, вільна для будь-якого використання) підключена напряму файлами в `app/Vendor/tfpdf/`, без Composer і без звернень до інтернету під час генерації. Шрифт DejaVu Sans (теж вбудований, без окремого встановлення) забезпечує коректний вивід кирилиці. При першому формуванні звіту бібліотека сама створює у `font/unifont/` кілька файлів кешу метрик шрифту (`*.mtx.php`, `*.cw.dat`, `*.cw127.php`) — це нормально й очікувано, вони прискорюють наступні звіти. **Важливо:** ці файли кешують абсолютний шлях до сервера, на якому створені, тому їх не можна переносити між серверами copy-paste'ом — при розгортанні на новому сервері (або оновленні через архів) видаліть їх, якщо вони випадково туди потрапили, і дайте папці `font/unifont/` право на запис (`install.sh`/`update.sh` роблять це автоматично) — бібліотека перестворить кеш правильно сама.

## Усунення несправностей

**HTTP 419 "Сесія застаріла" при відправленні форми.**
Це CSRF-захист (див. розділ «Безпека») — токен форми не збігається з токеном поточної сесії. Типові причини: форму тримали відкритою дуже довго в іншій вкладці до відправлення; користувача розлогінило (сесія завершилась) поки форма була відкрита; форму надіслано повторно з кешованої/збереженої сторінки. Рішення — просто оновити сторінку (F5) і заповнити форму заново. Якщо це трапляється систематично одразу після звичайного відкриття форми — перевірте, що сесії PHP взагалі зберігаються (права на запис у `session.save_path`, зазвичай `/var/lib/php/sessions` або `/tmp`).

**Порожня сторінка / 500 після входу.**
Найімовірніша причина — застосунок не може підключитися до БД (неправильні дані в `.env`, СУБД не запущена, або `.env` відсутній чи недоступний для читання користувачем веб-сервера). Перевірити:
```bash
sudo -u www-data php -r "print_r(require '/шлях/до/itsm-system/config/config.php');"
```
Якщо `.env` не знайдено — конфіг покаже дефолтні значення (`itsm` / `itsm_user` / `change_me`), і саме тому не з'єднається з реальною БД.
Деталі помилки — в лозі PHP/Apache: `tail -f /var/log/apache2/error.log` (шлях залежить від дистрибутива) або `tail -f /var/log/php-fpm/*.log`.

**Apache: "Not Found" на будь-якому URL, крім `/`.**
Не спрацьовує `.htaccess`. Перевірити:
```bash
sudo a2enmod rewrite && sudo systemctl restart apache2
```
і що в конфігу віртуального хоста для директорії `public/` виставлено `AllowOverride All` (за замовчуванням Apache часто ставить `AllowOverride None`, і тоді `.htaccess` повністю ігнорується).

**Nginx: 404 на всіх URL, крім `/`.**
Nginx не читає `.htaccess` (це суто apache-механізм) — для Nginx маршрутизацію потрібно прописати прямо в конфізі:
```nginx
location / {
    try_files $uri $uri/ /index.php?$query_string;
}
```

**Назви ролей, типів задач, статусів або ім'я адміністратора виглядають як "кракозябра" (наприклад, замість "Адміністратор" — щось на кшталт "Ð Ð´Ð¼Ñ–Ð½...").**
Це наслідок подвійного UTF-8-кодування при застосуванні `seed.sql` без прапорця `--default-character-set=utf8mb4` (виправлено в поточній версії `install.sh`, але могло статись при більш ранньому встановленні).

Найпростіше виправлення — одна команда (читає дані підключення з `.env` сам):
```bash
sudo bash update.sh
```

Або вручну:
```bash
# Перевірка (якщо текст нормальний — проблеми немає):
mysql -u root -p --default-character-set=utf8mb4 ІМ_Я_БД -e "SELECT name FROM roles;"

# Виправлення (прапорець --default-character-set=utf8mb4 ОБОВ'ЯЗКОВИЙ):
mysql -u root -p --default-character-set=utf8mb4 ІМ_Я_БД < database/migrations/002_fix_utf8_double_encoding.sql
```
Дані, введені через сам веб-інтерфейс (проєкти, задачі, коментарі, тікети, створені користувачами) цієї проблеми не мають — вона стосується лише довідників з `seed.sql`, застосованих напряму через shell.

## Перевірено

Повний цикл (логін → дашборд → створення проєкту → створення задачі → перегляд задачі → коментар → облік часу → тікет → адмін-панель) протестовано локально на PHP 8.3 + MariaDB 10.11 через вбудований веб-сервер PHP. Синтаксис усіх файлів перевірено `php -l`.

Додатково для v0.1.0:
- CSRF: відсутність токена → HTTP 419; правильний токен → успішне виконання (перевірено на логіні, створенні проєкту/задачі/тікета).
- Валідація білих списків: некоректні значення `visibility`/`priority`/`type_id`/`status` коректно відхиляються з дружнім повідомленням; коректні — проходять.
- Регресія: повний цикл усіх основних дій пройдено з чистими логами PHP (без warning/notice/error).
- Обмеження видимості: сторонній користувач не бачить чужий проєкт/тікет/задачу ні в списку, ні за прямим URL (403); після призначення відповідальним/оператором доступ з'являється миттєво.
- Канбан-дошка: симуляція точного AJAX-запиту перетягування картки підтвердила реальну зміну статусу задачі в БД.
- Календар: задача з датою початку й терміном виконання (5-денний діапазон) коректно з'явилась рівно двічі — на першому дні («▶») і на останньому («◀»), а дні між ними підтверджено порожні (перевірено напряму, що дні 11–13 із діапазону 10–14 не містять задачі); задача, що перетинає межу місяця, показує «▶» лише в місяці реального початку і «◀» лише в місяці реального завершення, по одному разу в кожному; одноденна задача (лише `due_date`) показується один раз без стрілок; навігація між місяцями і захист від некоректних `?month=` параметрів перевірені.
- Діаграма Ганта: міграцію `003_add_task_start_date.sql` перевірено на схемі без колонки (застосувалась і показала ідемпотентність); валідація порядку дат (початок > кінець) відхиляється і при створенні задачі, і при drag-редагуванні (422 + JSON); залежність між задачами (`blocked_by`) записана в БД і відображена стрілкою; симуляція AJAX-запиту `on_date_change` підтвердила реальне збереження нових дат.
- Дорожня карта: під час розробки сам виявив і виправив помилку в порядку таблиць `schema.sql` (`tasks.milestone_id` посилався на `milestones`, якої на той момент ще не було в файлі вище — MySQL не дозволяє forward-посилання між `CREATE TABLE`, довелось переставити таблиці місцями до першого ж тесту). Після виправлення: свіжа схема застосувалась без помилок; міграцію `004_add_milestones.sql` перевірено на старій схемі (застосувалась, показала ідемпотентність); прогрес-бар етапу коректно порахував «1 з 2 задач закрито (50%)»; крос-проєктна прив'язка задачі до етапу іншого проєкту відхилена; видалення етапу коректно занулило `milestone_id` у прив'язаній задачі, не видаливши саму задачу (`ON DELETE SET NULL`); перевірено обидва рівні захисту — 403 для сторонньої людини без доступу до проєкту, і окремо 403 за роллю (недостатньо прав) для людини з доступом, але без ролі admin/it_manager.
- **Аудит і оптимізація коду** (за прямим запитом): систематично перевірив кожен публічний метод кожної моделі й Core-класу на реальне використання. Під час першого проходу **мало не видалив робочий метод** `Ticket::all()`, прийнявши його за мертвий код — мій пошук шукав виклики виду `Ticket::method()`, а `allVisibleTo()` викликає його як `self::all()`, що під цей патерн не підпадало. Одразу повернув метод і переробив пошук з урахуванням `self::`/`static::`, а також розширив область пошуку на `public/` (де живе `public/index.php` — там само мало не пропустив реальне використання `Auth::start()`). Після виправлення методики знайдено й підтверджено рівно два справді мертві методи (`Project::updateStatus()`, ніколи не підключений до жодного маршруту, і застарілі докблоки-дублікати від попередніх перейменувань) — видалені. Окремо знайдено й виправлено **реальний N+1-запит** у дорожній карті (`Task::forMilestone()` викликався окремим SQL-запитом на кожен етап; замінено на один запит `Task::forProjectMilestones()` з групуванням у PHP) — перевірено наживо на 3 етапах і 3 задачах, групування зійшлося точно. Додано індекс `idx_time_logs_log_date` (міграція `005_add_time_logs_date_index.sql`) — колонка активно фільтрується й групується в кожному звіті обліку часу, доданому цієї сесії, але (на відміну від колонок-зовнішніх ключів, які InnoDB індексує автоматично) сама не мала індексу; міграцію перевірено на старій схемі, а **весь `update.sh` прогнано end-to-end з нуля** на відтвореному старому розгортанні — усі 8 кроків відпрацювали правильно, індекс підтверджено створеним у БД. Виправлено неточний коментар у `Csrf.php` (стверджував, що перевірка централізована в `public/index.php`, а насправді — в `Router::dispatch()`).
- Облік часу (історія на задачі + зведена сторінка проєкту): перевірено на реальному сценарії з двома користувачами й трьома записами на двох задачах. Під час тестування двічі сам ловив помилки у власних тестових curl-скриптах (не в застосунку) — спершу забув, що видимість проєкту поширюється й на облік часу (другий користувач без прав на проєкт отримував 403 при спробі відкрити задачу — це правильна поведінка, а не баг), а потім переплутав вивід `-w` з результатом `grep` в одній підстановці команди, через що CSRF-токен зіпсувався і один запис часу загубився. Після виправлення обох помилок: загальна сума на сторінці `/projects/{id}/time` показала точні **8.00 годин** (2.5 + 4 + 1.5), розбивка по користувачах — точні суми на кожного (5.50 та 2.50) у правильному порядку спадання; історія на сторінці задачі показала обидва записи другого користувача; сторонній користувач без доступу до проєкту отримав 403 на сторінці обліку часу проєкту.
- Загальний облік часу адміністратора (`/admin/time`): перевірено на двох **різних** проєктах, створених двома різними користувачами (адмін і `it_manager`) — загальна сума показала точні 8.00 годин (3+5), розбивка і по проєктах, і по учасниках дала точні суми в правильному порядку; для ролі `it_manager` (не адмін) сторінка коректно повертає 403.
- Розбивка обліку часу по днях/тижнях/місяцях: перевірено на записах, навмисно рознесених по різних періодах — два записи в один день (2+1 год) коректно підсумувались в один рядок «01.09.2026 → 3.00»; тиждень визначено за ISO 8601 (`2026-W36`, `2026-W37`, `2026-W41` — саме ті номери тижнів, що дав контрольний SQL-запит `WEEK(date, 3)` напряму); місяць підсумував записи з різних тижнів правильно («09.2026 → 8.00» = 3+5, «10.2026 → 7.00»). Та сама логіка перевірена ідентично й на глобальній сторінці `/admin/time`.
