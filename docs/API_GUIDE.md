# Гайд з інтеграції: REST API і вебхуки — ITSM System

*Версія застосунку: 0.2.3*

Цей документ — для тих, хто пише інтеграції: підключає моніторинг, месенджер, скрипти автоматизації чи інші ІТ-системи. Як **увімкнути** API, видати токени й налаштувати вебхуки в інтерфейсі — у `ADMIN_GUIDE.md`, розділи 18 і 19. Тут — що саме можна робити й як.

Два способи інтеграції доповнюють один одного:

| Потрібно | Використовуйте |
|---|---|
| Створити тікет чи задачу, змінити статус, додати коментар, прочитати дані | **REST API** — ви звертаєтесь до ITSM |
| Дізнаватись про зміни одразу, не опитуючи API щохвилини | **Вебхуки** — ITSM сам надсилає вам подію |

## 1. Швидкий старт

1. Адміністратор вмикає API (Адмін-панель → Налаштування → API). За замовчуванням воно **вимкнене**.
2. Отримайте токен: у своєму профілі («Мій профіль» → «Токени доступу до API») або від адміністратора. Токен виглядає як `itsm_` і 48 символів `0-9a-f`. Його показують **один раз** — збережіть одразу.
3. Перевірте підключення:

```bash
curl -H "Authorization: Bearer itsm_ВАШ_ТОКЕН" https://itsm.example.org/api/v1/me
```

Відповідь:

```json
{
  "data": {
    "user": { "id": 3, "full_name": "Монітор Zabbix", "email": "zabbix@example.org", "role": "requester" },
    "token": { "name": "doc-zabbix", "scope": "write", "expires_at": "2027-01-05T09:05:33+00:00" }
  }
}
```

4. Створіть тікет (потрібен токен із правом **запису**):

```bash
curl -X POST https://itsm.example.org/api/v1/tickets \
  -H "Authorization: Bearer itsm_ВАШ_ТОКЕН" \
  -H "Content-Type: application/json" \
  -d '{"queue_id": 1, "subject": "Диск /var заповнено на 95% (srv-db01)", "description": "Trigger: disk usage > 95%. Хост: srv-db01."}'
```

Той самий запит мовою Python (без сторонніх бібліотек):

```python
import json, urllib.request

TOKEN = "itsm_ВАШ_ТОКЕН"
req = urllib.request.Request(
    "https://itsm.example.org/api/v1/tickets",
    data=json.dumps({"queue_id": 1, "subject": "Диск /var заповнено на 95% (srv-db01)"}).encode("utf-8"),
    headers={"Authorization": "Bearer " + TOKEN, "Content-Type": "application/json"},
    method="POST",
)
with urllib.request.urlopen(req) as resp:
    ticket = json.load(resp)["data"]
print(ticket["id"], ticket["url"])
```

## 2. Загальні правила

**Адреса й формат.** Усі маршрути — під `/api/v1`. Запити й відповіді — JSON у кодуванні UTF-8 (кирилиця не екранується). Версія `v1` змінюється лише несумісними змінами; додавання нових полів у відповіді несумісною зміною не вважається — клієнт має ігнорувати поля, яких не знає.

**Автентифікація.** Заголовок `Authorization: Bearer <токен>`. Запасний варіант для проксі, що вирізають `Authorization`, — заголовок `X-Api-Token: <токен>`. Токен в адресі запиту (`?token=…`) **не підтримується** навмисно: адреси потрапляють у логи й історію браузера. Cookie і сесії API **ігнорує повністю**.

**Права = права власника токена.** Токен діє від імені користувача, якому належить: та сама роль, та сама видимість проєктів, задач і тікетів, що й у веб-інтерфейсі. Зміна ролі користувача діє на токен негайно. Якщо запис існує, але недоступний цьому користувачеві, API відповідає **404** (а не 403) — щоб не підтверджувати існування прихованого.

**Права токена (scope).** `read` — лише `GET`; `write` — ще й `POST` та `PATCH`. Токен `read` на запис отримує `403 insufficient_scope`.

**Дати.** ISO 8601 із зсувом часового поясу сервера: `2026-10-07T09:05:39+00:00`. Дати без часу (`start_date`, `due_date`) — `РРРР-ММ-ДД`.

**Пагінація.** У списках: `?page=1&per_page=25` (за замовчуванням 25, максимум 100; некоректні значення замінюються типовими). Відповідь:

```json
{ "data": [ … ], "meta": { "page": 2, "per_page": 10, "total": 35, "pages": 4 } }
```

Пагінуються `/projects`, `/projects/{id}/tasks`, `/tasks`, `/tickets`, `/users`. Довідники (`/ticket-queues`, `/task-statuses`, `/task-types`) та `/projects/{id}/members` повертають усе одним масивом `data`.

**Обмеження частоти.** Окремо на кожен токен, за замовчуванням 120 запитів на хвилину (змінює адміністратор). У кожній відповіді: `X-RateLimit-Limit`, `X-RateLimit-Remaining`, `X-RateLimit-Reset` (секунд до нового вікна). Понад ліміт — `429 rate_limited` із заголовком `Retry-After`.

**Тіло запиту.** Для `POST` і `PATCH` — JSON-**об'єкт** із заголовком `Content-Type: application/json`, не більше 1 МБ.

**Повтори й дублі.** Створення (`POST`) **не ідемпотентне**: повторний запит створить ще один запис. Якщо відповіді не дочекались, перевірте через `GET`, чи запис уже є, перш ніж повторювати.

### Помилки

Усі помилки — одного формату:

```json
{ "error": { "code": "validation_failed", "message": "Некоректні дані запиту.",
             "details": { "queue_id": "Такої черги немає (див. GET /api/v1/ticket-queues).", "subject": "Обов'язкове поле." } } }
```

`code` — стабільний ідентифікатор, за ним пишіть логіку клієнта; `message` — текст для людини й може змінюватись; `details` (лише для 422) — пояснення по полях.

| HTTP | `code` | Коли |
|---|---|---|
| 400 | `invalid_json` | Тіло — не коректний JSON-об'єкт |
| 401 | `unauthenticated` | Немає токена чи він недійсний (**однакова** відповідь для відкликаного, простроченого, неіснуючого й токена деактивованого користувача) |
| 403 | `insufficient_scope` | Токен лише для читання, а запит змінює дані |
| 404 | `not_found` | Немає запису, або він недоступний власнику токена; або такого маршруту немає |
| 405 | `method_not_allowed` | Метод не підтримується (заголовок `Allow` перелічує дозволені) |
| 413 | `payload_too_large` | Тіло понад 1 МБ |
| 415 | `unsupported_media_type` | Не `application/json` |
| 422 | `validation_failed` | Некоректні поля (`details` вказує які) |
| 429 | `rate_limited` | Перевищено ліміт запитів |
| 500 | `server_error` | Збій на сервері; у повідомленні — код інциденту, за яким адміністратор знайде причину в `storage/logs` |
| 503 | `api_disabled` | API вимкнено адміністратором |
| 503 | `api_unavailable` | На сервері не виконано оновлення БД (`update.sh`) |

## 3. Довідник маршрутів

| Метод і шлях | Призначення | Право |
|---|---|---|
| `GET /api/v1/me` | Хто я за цим токеном | read |
| `GET /api/v1/ticket-queues` | Черги тікетів | read |
| `GET /api/v1/task-statuses` | Статуси задач (`id`, `code`, `name`, `is_closed`) | read |
| `GET /api/v1/task-types` | Типи задач | read |
| `GET /api/v1/users` | Активні користувачі (email — лише для адміністратора й керівника ІТ) | read |
| `GET /api/v1/projects` | Проєкти, видимі власнику токена | read |
| `GET /api/v1/projects/{id}` | Один проєкт | read |
| `GET /api/v1/projects/{id}/tasks` | Задачі проєкту | read |
| `GET /api/v1/projects/{id}/members` | Учасники проєкту (яким надано доступ) | read |
| `POST /api/v1/projects/{id}/tasks` | Створити задачу в проєкті | write |
| `GET /api/v1/tasks` | Задачі, видимі власнику токена | read |
| `GET /api/v1/tasks/{id}` | Задача з коментарями | read |
| `PATCH /api/v1/tasks/{id}` | Змінити статус, виконавця, опис, терміни, етап | write |
| `POST /api/v1/tasks/{id}/comments` | Коментар до задачі | write |
| `GET /api/v1/tickets` | Тікети, видимі власнику токена | read |
| `POST /api/v1/tickets` | Створити тікет | write |
| `GET /api/v1/tickets/{id}` | Тікет з коментарями | read |
| `PATCH /api/v1/tickets/{id}` | Змінити статус, оператора | write |
| `POST /api/v1/tickets/{id}/comments` | Коментар до тікета | write |

Видалення через API **не передбачене**: `DELETE` відповідає 405.

### Фільтри списків

| Список | Параметри |
|---|---|
| `/projects` | `status` (`active`, `archived`, `closed`), `q` (частина назви) |
| `/projects/{id}/tasks` | `status_id`, `open=1` (лише незакриті) |
| `/tasks` | `project_id`, `assignee_id`, `status_id`, `priority` (`low`, `normal`, `high`, `critical`), `q` (частина назви), `include_closed=1` (за замовчуванням лише відкриті) |
| `/tickets` | `status` (`new`, `in_progress`, `waiting_customer`, `resolved`, `closed`), `queue_id`, `q` (частина теми), `assigned_to_me=1`, `requested_by_me=1` |

Невідоме значення `status` чи `priority` дає 422, а не порожній список.

### Створення тікета — `POST /api/v1/tickets`

| Поле | Обов'язкове | Правила |
|---|---|---|
| `queue_id` | так | id черги з `/ticket-queues` |
| `subject` | так | до 255 символів |
| `description` | ні | до 20 000 символів |
| `project_id` | ні | проєкт, до якого власник токена має доступ |

Заявником стає **власник токена**. Поля `requester_*` у тілі ігноруються: створити тікет «від імені» іншої людини не можна. Для інтеграцій заведіть окремого службового користувача (наприклад, «Моніторинг Zabbix») — тоді тікети й коментарі видно як створені ним. Відповідь — `201` і тікет:

```json
{ "data": {
    "id": 2, "subject": "Диск /var заповнено на 95% (srv-db01)", "description": "Trigger: disk usage > 95%. Хост: srv-db01.",
    "status": "new", "queue": { "id": 1, "name": "Загальна підтримка" },
    "requester": { "user_id": 3, "name": "Монітор Zabbix", "email": "zabbix@example.org" },
    "operator": null, "project": null, "csat_score": null, "first_response_at": null, "resolved_at": null,
    "created_at": "2026-10-07T09:05:39+00:00", "updated_at": "2026-10-07T09:05:39+00:00",
    "url": "https://itsm.example.org/tickets/2" } }
```

### Зміна тікета — `PATCH /api/v1/tickets/{id}`

Дозволені поля: `status` та `operator_id` (`null` знімає оператора). Інші (`subject`, `requester_email` тощо) — 422 із поясненням. Особливості:

- Призначати оператора можуть лише ролі «Адміністратор», «Керівник ІТ-підрозділу», «Оператор служби підтримки» (як і у веб-інтерфейсі); оператор має бути **активним** користувачем.
- Запит застосовується **цілком або зовсім ні**: якщо `status` коректний, а `operator_id` — ні, не зміниться нічого (422).
- Значення, що не змінюються (той самий статус), нічого не пишуть у журнал аудиту й не викликають подій.

```bash
curl -X PATCH https://itsm.example.org/api/v1/tickets/2 \
  -H "Authorization: Bearer itsm_ТОКЕН_ОПЕРАТОРА" -H "Content-Type: application/json" \
  -d '{"status": "in_progress", "operator_id": 2}'
```

### Коментар — `POST /api/v1/tickets/{id}/comments` і `…/tasks/{id}/comments`

Тіло: `{"body": "Текст"}`, 1–20 000 символів. Відповідь — `201` і коментар:

```json
{ "data": { "id": 2, "author_type": "requester", "author": { "id": 3, "full_name": "Монітор Zabbix" },
            "body": "Проблема триває вже 15 хвилин.", "created_at": "2026-10-07T09:05:39+00:00" } }
```

Для тікетів `author_type` визначається роллю власника токена (`operator` для адміністратора й оператора служби підтримки, інакше `requester`) — так само, як у веб-формі.

### Створення задачі — `POST /api/v1/projects/{id}/tasks`

| Поле | Обов'язкове | Правила |
|---|---|---|
| `title` | так | до 255 символів |
| `type_id` | так | id із `/task-types` |
| `priority` | ні | `low`, `normal` (за замовчуванням), `high`, `critical` |
| `description` | ні | до 20 000 символів |
| `assignee_id` | ні | активний користувач |
| `start_date`, `due_date` | ні | `РРРР-ММ-ДД`; початок не пізніше терміну |
| `milestone_id` | ні | етап **цього ж** проєкту |

Початковий статус — «Нова». Відповідь — `201` і задача (`project`, `type`, `status`, `priority`, `author`, `assignee`, `start_date`, `due_date`, `milestone`, `url`).

### Зміна задачі — `PATCH /api/v1/tasks/{id}`

Дозволені поля: `status` (код зі `/task-statuses`) **або** `status_id`, `assignee_id`, `description`, `start_date`, `due_date`, `milestone_id`. `null` знімає виконавця, етап чи дату. Назву, пріоритет, тип і проєкт через API змінити не можна (422). Правила атомарності й «без шуму» — ті самі, що й для тікетів. Дати перевіряються разом із поточними: новий `due_date` раніше за наявний `start_date` — 422.

## 4. Вебхуки: події від ITSM

Вебхук — це адреса, на яку ITSM надсилає `POST` із JSON, коли в системі щось сталося. Адміністратор створює вебхук у Адмін-панель → Налаштування → Вебхуки: адреса, перелік подій (або всі), перевірка TLS. При створенні показується **секрет** — ним підписується кожен запит.

### Події

| Подія | Коли |
|---|---|
| `ticket.created` | Створено тікет (веб, портал, лист або API) |
| `ticket.status_changed` | Змінено статус тікета |
| `ticket.assigned` | Призначено чи знято оператора (зокрема автопризначення при створенні) |
| `ticket.comment_added` | Новий коментар (зокрема відповідь листом і коментар із порталу) |
| `ticket.rated` | Заявник оцінив вирішення (CSAT) |
| `task.created` | Створено задачу |
| `task.status_changed` | Змінено статус задачі |
| `task.assigned` | Змінено виконавця |
| `task.updated` | Змінено опис, терміни, етап чи проєкт |
| `task.comment_added` | Новий коментар до задачі |
| `task.deleted` | Видалено задачу |
| `project.created` | Створено проєкт |
| `project.status_changed` | Змінено статус проєкту |
| `project.responsible_changed` | Змінено відповідального |
| `project.member_added` | Користувачу надано доступ до проєкту |
| `project.member_removed` | У користувача забрано доступ |
| `project.deleted` | Видалено проєкт |

Окрема службова подія `webhook.ping` надсилається кнопкою «Надіслати тестову подію» — вона не входить до переліку підписки.

### Що приходить

`POST` на вашу адресу, `Content-Type: application/json; charset=utf-8`, із заголовками:

| Заголовок | Значення |
|---|---|
| `X-ITSM-Event` | Код події, наприклад `ticket.created` |
| `X-ITSM-Event-Id` | UUID події — **однаковий при всіх повторах** однієї доставки; за ним дедуплікуйте |
| `X-ITSM-Delivery` | Номер доставки в журналі ITSM |
| `X-ITSM-Timestamp` | Unix-час відправки (секунди) |
| `X-ITSM-Signature` | `sha256=` і hex-підпис (див. нижче) |
| `User-Agent` | `ITSM-Webhook/1.0` |

Тіло:

```json
{
  "id": "a3731bed-56f4-4559-84a8-af5ae7374ad8",
  "event": "ticket.comment_added",
  "created_at": "2026-10-07T09:05:50+00:00",
  "actor": { "id": 1, "full_name": "Адміністратор Системи" },
  "via": "api",
  "data": {
    "id": 3, "subject": "Не працює VPN", "status": "new",
    "queue": { "id": 1, "name": "Загальна підтримка" },
    "requester": { "user_id": 3, "name": "Монітор Zabbix", "email": "zabbix@example.org" },
    "operator": null, "url": "https://itsm.example.org/tickets/3"
  },
  "comment": {
    "id": 3, "author_type": "operator", "author": { "id": 1, "full_name": "Адміністратор Системи" },
    "body": "Перевіряємо.", "created_at": "2026-10-07T09:05:50+00:00"
  }
}
```

(У прикладі `data` скорочено; повний склад полів — той самий, що в REST API для тікета, задачі чи проєкту.)

- `id` — UUID події (збігається з `X-ITSM-Event-Id`).
- `actor` — хто виконав дію; `null`, якщо її зробила система чи анонімний заявник (портал, лист від невідомого відправника).
- `via` — канал: `"api"` для дій через REST API, інакше `null` (веб-інтерфейс, портал, пошта).
- `data` — **поточний** стан об'єкта на момент події (той самий формат, що в REST API). Для `task.deleted` і `project.deleted` — останній стан перед видаленням.
- `comment` — є лише в подіях `*.comment_added`.
- `changes` — є, коли система зберегла подробиці зміни (наприклад, `{"member_user_id": 4}` для `project.member_added` чи `{"title": "…"}` для `task.deleted`). Не покладайтесь на його наявність.

У вебхуках **немає** паролів, службового `access_token` порталу й самого секрету.

### Перевірка підпису

Підпис = HMAC-SHA256 від рядка `<X-ITSM-Timestamp>.<сире тіло запиту>` ключем-секретом, у hex, з префіксом `sha256=`. Підписується й час, тому перехоплений запит не можна відтворити пізніше: відхиляйте запити, мітка часу яких відрізняється від поточного більш ніж на 5 хвилин. Підпис рахуйте від **сирих байтів** тіла, до розбору JSON, і порівнюйте у сталий час.

Python:

```python
import hmac, hashlib, time

def verify(secret: str, headers, raw_body: bytes, tolerance: int = 300) -> bool:
    ts = headers["X-ITSM-Timestamp"]
    if abs(time.time() - int(ts)) > tolerance:
        return False
    expected = "sha256=" + hmac.new(secret.encode(), ts.encode() + b"." + raw_body, hashlib.sha256).hexdigest()
    return hmac.compare_digest(expected, headers["X-ITSM-Signature"])
```

PHP:

```php
$raw = file_get_contents('php://input');
$ts = $_SERVER['HTTP_X_ITSM_TIMESTAMP'] ?? '';
$sig = $_SERVER['HTTP_X_ITSM_SIGNATURE'] ?? '';
$expected = 'sha256=' . hash_hmac('sha256', $ts . '.' . $raw, $secret);
$valid = abs(time() - (int) $ts) <= 300 && hash_equals($expected, $sig);
```

Node.js:

```javascript
const crypto = require('crypto');

function verify(secret, headers, rawBody, tolerance = 300) {
  const ts = headers['x-itsm-timestamp'];
  if (Math.abs(Date.now() / 1000 - Number(ts)) > tolerance) return false;
  const expected = 'sha256=' + crypto.createHmac('sha256', secret).update(ts + '.').update(rawBody).digest('hex');
  const given = Buffer.from(headers['x-itsm-signature'] || '');
  const want = Buffer.from(expected);
  return given.length === want.length && crypto.timingSafeEqual(given, want);
}
```

### Відповідь, повтори, дублі

- Відповідайте **2xx протягом 6 секунд** — це успіх. Будь-що інше (4xx, 5xx, таймаут, помилка з'єднання) — невдача.
- **Перенаправлення (3xx) не виконуються** і вважаються невдачею: вказуйте кінцеву адресу.
- Невдала доставка повторюється через **1 хв, 5 хв, 30 хв, 2 год, 12 год** (усього 6 спроб), потім отримує статус «невдало» й більше не надсилається (адміністратор може повторити її вручну в журналі).
- **20 невдалих доставок поспіль** автоматично вимикають вебхук; відповідь **410 Gone** вимикає його одразу. Адміністратор бачить причину й вмикає його знову.
- Гарантія — «**принаймні раз**»: через повтори й збої мережі одну подію можна отримати двічі. Дедуплікуйте за `id` події (`X-ITSM-Event-Id`).
- **Порядок не гарантується**: повтор старої події може прийти після нової. Орієнтуйтесь на `data.updated_at` або за потреби перечитайте об'єкт через REST API.
- Подія записується в чергу в тій самій транзакції, що й зміна. Якщо зміна не збереглась (збій, відкат), подія не надсилається.

### Обмеження адрес (захист від SSRF)

Дозволені лише `http://` і `https://` без логіна й пароля в адресі. Адреси **link-local** (169.254.0.0/16 — зокрема адреса метаданих хмарних серверів 169.254.169.254, fe80::/10), службові та мультикаст заборонені **завжди**. Внутрішні адреси (10.x, 172.16–31.x, 192.168.x, 127.x) за замовчуванням дозволені — вебхуки на внутрішні сервіси в корпоративній мережі є нормою; адміністратор може заборонити їх параметром `WEBHOOK_ALLOW_PRIVATE=false` у `.env`. Ім'я хоста розпізнається перед відправкою, а з'єднання йде на вже перевірену адресу — підміна DNS між перевіркою й запитом не діє.

## 5. Рекомендації

- **Окремий службовий користувач** для кожної інтеграції з мінімально потрібною роллю й токеном потрібного рівня (`read`, якщо запис не потрібен), із терміном дії. Зламаний токен дає ті самі права, що й користувач.
- **Не публікуйте токени й секрети** в репозиторіях і логах; зберігайте в змінних середовища чи сховищі секретів. Підозрюєте витік — відкличте токен (профіль чи Адмін-панель → Налаштування → API) і створіть новий; секрет вебхука замінюється кнопкою «Замінити секрет».
- **Не опитуйте API щохвилини**, щоб дізнатись про зміни: підпишіться на вебхук. Опитування — лише як запасний варіант, зі зростаючою паузою.
- **Обробляйте 429:** чекайте `Retry-After` секунд і повторюйте. Для `5xx` і помилок мережі — повторюйте з наростаючою паузою, але пам'ятайте про неідемпотентність `POST`.
- **Вебхук-одержувач:** відповідайте одразу (2xx), а важку обробку виконуйте асинхронно — інакше вкластись у 6 секунд не вдасться; перевіряйте підпис і мітку часу; дедуплікуйте за `id`.
- **Лише HTTPS.** Токен і секрет не повинні мандрувати відкритим каналом.

## 6. Обмеження поточної версії

- Немає видалення й масових операцій; змінювати можна лише перелічені поля (решта — тільки у веб-інтерфейсі).
- Немає завантаження вкладень через API (вкладення — у веб-інтерфейсі, зображення — також листом).
- Списки пагінуються на боці застосунку: на дуже великих обсягах (десятки тисяч записів) вони можуть відповідати повільно — звужуйте вибірку фільтрами.
- Немає ідемпотентних ключів для `POST`.
- Немає окремих прав на рівні токена до окремих проєктів чи черг: права токена дорівнюють правам його власника.
- Подій для вкладень, аудиторських записів і користувачів поки немає.
